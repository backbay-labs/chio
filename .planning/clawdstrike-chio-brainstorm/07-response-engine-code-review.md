# Clawdstrike Response Engine Code Review

Line numbers refer to the clawdstrike working tree on branch `fix/macos-es-ne-hardening`, 17 May 2026. `edr.rs` = `crates/libs/clawdstrike-policy-event/src/edr.rs` (20,413 lines). `api_server.rs` = `apps/agent/src-tauri/src/api_server.rs` (45,497 lines, not the 45,413 cited by the prior audit; both prior counts were off).

## Data model - what is actually there

- Plan input is `EndpointResponsePlan` (edr.rs:2646-2659) with 12 fields: `action_id`, `action`, `dry_run`, `root_node_id`, `graph_slice_id`, `ttl_seconds`, `rollback_ref`, `reason`, `created_at`, `expires_at`, `node_count`, `edge_count`. `expires_at` is derived: `created_at + Duration::seconds(ttl_seconds as i64)` (edr.rs:2853). TTL is validated 1..=`EDR_MAX_RESPONSE_TTL_SECONDS` by `validate_response_action_ttl_seconds` (api_server.rs:10844). There is no separate `issued_at`; `created_at` plays that role. `rollback_ref` is a string handle, not a typed reference; for `CollectEvidence` non-dry-run it is formatted `"rollback:noop:{action_id}"` (edr.rs:2848), otherwise `"rollback:{action_id}"` (edr.rs:2850).
- The peer's "ExecutionRecord" is actually `EndpointResponseExecutionReport` (edr.rs:3170-3189). Fields: `execution_id`, `action_id`, `action`, `status`, `dry_run`, `root_node_id`, `graph_slice_id`, `ttl_seconds`, `rollback_ref`, `reason`, `started_at`, `completed_at`, `evidence_bundle`, `actor: Option<EndpointDecisionActor>`, `effects: Vec<EndpointResponseExecutionEffect>`, `summary`. Per-action constructors at edr.rs:3216 (collect_evidence), 3353 (restrict_egress), 3441 (quarantine_file), 3521 (disable_persistence), 3586 (revoke_grant), 3669 (suspend_process_tree), 3734 (terminate_process_tree); failure variant at 3283.
- `EndpointResponseExecutionEffect` (edr.rs:2920-2929) has six fields: `effect_id`, `effect_type`, `target`, `artifact`, `content_hash`, `byte_count`. Effect constructors include forward and inverse pairs: quarantine_file/restore_quarantine_file (edr.rs:2933/2957), disable_persistence/restore_persistence_file (2981/3005), restrict_egress/restore_egress (3044/3067), suspend_process_tree/resume_process_tree (3104/3142, but inspection of edr.rs:3142 actually returns a terminate_process_tree effect - this is the constructor for the forward terminate; resume_process_tree is around 3104), plus revoke_grant (3029). There is no `restore_revoke_grant` or `restore_terminate_process_tree`.
- `EndpointDecisionAction` enum has 12 variants (edr.rs:2304-2318): Allow, Observe, Warn, Alert, Block, RestrictEgress, SuspendProcessTree, TerminateProcessTree, QuarantineFile, RevokeGrant, DisablePersistence, CollectEvidence. The first five are observation-only verdicts; the latter seven dispatch to live executors when `dry_run = false` (api_server.rs:11076-11106). Note: `Block` is in the enum but has no executor branch - it is rendered by upstream PolicyDecision receipts, not by ResponseAction.
- Rollback receipt = `EndpointResponseRollbackReport` (edr.rs:3886-3904). It links back via `execution_id` (edr.rs:3890) and `action_id` (3891) and inherits the same `rollback_ref` and `root_node_id`. Rollback constructors only exist for four actions: restrict_egress (3929), quarantine_file (4002), disable_persistence (4066), suspend_process_tree (4132). No constructor for TerminateProcessTree, RevokeGrant, or CollectEvidence.
- Acknowledgement receipt = `EndpointResponseAcknowledgementReport` (edr.rs:4278-4296). Fields include `acknowledgement_id`, `execution_id`, `action_id`, `acknowledged_by`, optional `note`, `acknowledged_at`, optional `control_correlation: Option<EndpointResponseControlCorrelation>` (edr.rs:4250-4260). The control correlation carries `response_action_id`, `delivery_id`, `target_kind`, `target_id`, `ack_token_hash`, `ack_status`, `resulting_state` - the postback identity, not a second signature.

## Executors - what runs and what does not

- QuarantineFile - REAL. `execute_quarantine_file_response` (api_server.rs:11198) reads bytes, hashes, calls `fs::rename(&source_path, &quarantine_path)` at api_server.rs:11260. Destination is under `state.edr_quarantine_root` (11229), reversible by inverse rename to the original path.
- DisablePersistence - REAL. `execute_disable_persistence_response` (api_server.rs:11280) hashes, then `fs::rename(&source_path, &disabled_path)` at api_server.rs:11347. Move target is the same quarantine_root (api_server.rs:11311 reuses `edr_quarantine_root`). Reversible by inverse rename.
- SuspendProcessTree - REAL. `execute_suspend_process_tree_response` (api_server.rs:11423) loops over targets in reverse order and calls `signal_process(target.pid, process_suspend_signal())` at api_server.rs:11460. `process_suspend_signal()` returns `libc::SIGSTOP` on Unix (api_server.rs:12799). `signal_process` calls `unsafe { libc::kill(pid, signal) }` at api_server.rs:12842. Rollback issues `libc::SIGCONT` (api_server.rs:12809, called from api_server.rs:11802).
- TerminateProcessTree - REAL, but SIGTERM, not SIGKILL. `execute_terminate_process_tree_response` (api_server.rs:11485) calls `signal_process(target.pid, process_terminate_signal())` at api_server.rs:11521. `process_terminate_signal()` returns `libc::SIGTERM` (api_server.rs:12819). The prior peer's claim "no SIGKILL" is literally true but misleading; the executor IS implemented. There is no rollback executor - `execute_terminate_process_tree_rollback` does not exist, and the rollback router rejects it (api_server.rs:18293-18306). The skeptical audit's earlier note about SIGTERM was correct.
- RevokeGrant - REAL with three target arms. `execute_revoke_grant_response` (api_server.rs:11367) dispatches on `RevokeGrantTarget`: `LocalApiAuthToken` (11388 - calls `rotate_local_api_token_without_grace`), `BrokerCapability { capability_id }` (11392 - calls `revoke_broker_capability_grant`), `LocalIntegrationSecret` (11402 - calls `revoke_local_integration_secret_grant`). The broker path is real, contradicting the peer's claim. No rollback executor exists.
- RestrictEgress - REAL via NE policy file. `execute_restrict_egress_response` is at api_server.rs:11163. The flow writes restrictions to the egress ledger and then `sync_edr_network_extension_egress_policy` (api_server.rs:11921) writes the policy snapshot file at `state.edr_network_extension_egress_policy_path` and calls `state.macos_host.request_network_extension_reload(...)` (api_server.rs:11949) - so the NE reload IS actively requested, not waiting on a file-watcher.
- CollectEvidence - REAL but evidence-only. `execute_collect_evidence_response` (api_server.rs:11144) stores the evidence bundle and emits receipts; no destructive side effect, no rollback needed (correctly rejected at api_server.rs:18293).
- No other action variants have executors; api_server.rs:11098-11104 returns BAD_REQUEST for any other action.

## TTL enforcement gap - verified

The peer's claim holds. `agent_edr_response_execution_expire` (api_server.rs:18030) is the HTTP handler; route mounted at api_server.rs:705-706 (`POST /api/v1/agent/edr/response-executions/expire`). It scans the ledger via `pending_expiring_executions` (api_server.rs:23804), executes rollback for the four rollback-capable actions via `execute_response_expiration_rollback` (api_server.rs:11570), then calls `expire_due` (api_server.rs:23747) to append expired records.

There is no background scheduler. `grep tokio::spawn` and `tokio::time::interval` across api_server.rs and main.rs finds exactly one repeating loop: `fleet_agent_secret_touch_sync_loop` (api_server.rs:8291), with the interval at api_server.rs:8297 - that loop drains fleet hunt event outboxes and publishes secret touches; it never calls the expire handler or scans the response execution ledger. main.rs (1357 lines) has zero references to response-execution expiry.

Operational implication: if no caller hits `/expire`, an expired execution sits in the ledger past `expires_at` and its side effect remains live. The peer flagged this as the central missing piece for a bounded-action claim, and the code confirms it.

## Rollback invariants - what holds

- restrict_egress rollback (api_server.rs:11542) deactivates the egress ledger entry then re-syncs the NE policy file (api_server.rs:11556). The rollback report constructor (edr.rs:3929) reconstructs the target set from the original effect's artifact (csv of targets) and checks the inverse content_hash matches before producing the rollback (edr.rs:3967-3973). Truly inverse subject to NE reload succeeding.
- quarantine_file rollback (api_server.rs:11598) reads the artifact, hashes it, compares to the recorded `content_hash` (api_server.rs:11646-11653) and byte count (11654-11663), refuses if the original target_path now exists (api_server.rs:11616-11624), then `fs::rename(&artifact_path, &target_path)` (api_server.rs:11673). This is the only rollback that defends against the "the original path has been overwritten" race - it just refuses to overwrite. A user that wrote a new file in the meantime gets a 409. Truly inverse if the original path is empty.
- disable_persistence rollback (api_server.rs:11685) has the same structure: existence check (11703), hash check (11738), inverse rename (11770). Same crash-safety profile as quarantine_file.
- suspend_process_tree rollback (api_server.rs:11782) issues SIGCONT to each pid (api_server.rs:11802). Note: it does NOT verify the pid still exists or that the recorded pid set matches the live process tree; a pid that has since died will fail open at the kernel level but the rollback could still mark itself succeeded for the surviving pids. This is not crash-symmetric.
- Rollback receipt is produced by `EndpointDecisionReceipt::for_response_rollback` (edr.rs:5737-5802) and signed; receipt evidence at edr.rs:5772-5790 carries `rollbackId`, `executionId`, `responseActionId`, `rollbackRef`, `rollbackStatus`. The rollback's `execution_id` field (edr.rs:3890) ties it to the original execution receipt by id.
- Races: TTL expiry calls into the same rollback functions (api_server.rs:11570-11596). If a manual rollback and a TTL-driven rollback fire concurrently, both contend on the same egress ledger mutex (api_server.rs:11551) or both attempt the same `fs::rename` (the second will fail with ENOENT). There is no per-execution rollback lock; the egress ledger mutex serializes egress rollbacks but the file-rename rollbacks rely on filesystem-level atomicity of `rename(2)` for safety. For quarantine and disable_persistence, the `target_path.exists()` precheck (api_server.rs:11616, 11703) plus subsequent `fs::rename` is not atomic - a TOCTOU race exists, but it manifests as both rollback attempts trying the rename and one losing.

## Signing path - what each receipt carries

- A single Ed25519 keypair signs every receipt family. `EndpointReceiptLedger::open` (api_server.rs:19750) loads or creates the keypair at api_server.rs:19753 via `load_or_create_edr_receipt_signer`. All `sign_*` methods sign with `&self.keypair` (api_server.rs:19817, 19856, 19880, etc.). So SensorState / PolicyDecision / ResponseExecution / ResponseRollback / ResponseAcknowledgement / EvidenceBundleManifest are signed by the same endpoint key. No bilateral signing wired.
- Every receipt carries `policy: EndpointPolicySnapshot` with version+hash+epoch (edr.rs:2289-2293). Every receipt input struct includes a `policy` field (e.g. edr.rs:4904, 4915, 4926, 4937).
- Every receipt carries `sensor_state: EndpointSensorState` (e.g. edr.rs:4905, 4916, 4927, 4938). Only the execution receipt's emitter pulls a real snapshot: `endpoint_sensor_state_from_macos_host(&macos_host)` at api_server.rs:20805. Rollback and acknowledgement emitters fall back to `EndpointSensorState::single_active_agent("agent-api")` (api_server.rs:20833, 20851) - a placeholder default that names a single fictional active provider. The plan receipt also uses the placeholder (api_server.rs:20784). This is a real fidelity gap: a constitution that requires sensor-attested rollbacks would see synthetic data on the rollback receipt.
- Canonical-JSON layout uses `hush_core::canonicalize_json` (api_server.rs:71), an RFC 8785-style sort-by-key. Receipt evidence keys are camelCase strings and sort deterministically. There is targeted coverage for the privacy report (`agent_edr_privacy_report_suppresses_raw_observation_artifacts_by_default` at api_server.rs:31824) and dedicated checks that ResponseExecution receipts carry `executionEffect:` evidence rows (api_server.rs:43590-43596), but no explicit test that names canonical-byte stability of a ResponseRollback receipt across rebuilds.

## Acknowledgement loop - what is wired

`POST /api/v1/agent/edr/response-executions/{id}/acknowledge` (api_server.rs:734) dispatches to `agent_edr_response_execution_acknowledge` (api_server.rs:19330). State transition: it loads the execution from the ledger (19369), loads the matching graph from the evidence bundle store (19381), constructs `EndpointResponseAcknowledgementReport::from_execution` (19399), optionally wraps in `with_control_correlation` (19405), appends to `edr_response_acknowledgement_ledger` (19406), signs the receipt (19407), then optionally POSTs the acknowledgement back to the control plane via `post_control_response_acknowledgement` (19412). No execution status mutation on the execution ledger - the acknowledgement is an additive receipt event, not a state machine transition on the underlying execution.

`GET /api/v1/agent/edr/response-executions/{id}/proof` (api_server.rs:738) dispatches to `agent_edr_response_execution_proof` (api_server.rs:17924). It returns an `EdrResponseExecutionProofResponse` bundle: the execution record, the graph, the provider/sensor state, plus six families of SignedReceipt - the request receipt, the execution receipt, the evidence-bundle-manifest receipt, lifecycle transition receipts, rollback receipts, acknowledgement receipts (api_server.rs:18015-18027). It also calls `verify_response_execution_proof_actor_continuity` (api_server.rs:17995) to assert actor identity matches across the receipt chain. This is a clawdstrike-internal proof structure (a JSON envelope of SignedReceipts), not an in-toto statement or a DSSE bundle - the SignedReceipts use the hush-core receipt envelope, not in-toto/DSSE.

Control-plane handler: `post_control_response_acknowledgement` (referenced in api_server.rs:19412, around api_server.rs:19193) takes a `control_api_url` and posts the acknowledgement; this is endpoint-initiated, not control-plane-initiated. There is no control-plane-side handler in this codebase; the postback assumes an external endpoint.

## Missing pieces relative to the theorem

The proposed theorem is `bounded_executive_action_safety_requires_ttl_and_rollback`: every admitted enforcement action either terminates within its declared TTL or carries a rollback receipt closing it. For an empirical chapter to point at this codebase, the gaps are:

1. Background TTL reaper. The `/expire` endpoint exists but no background scheduler invokes it. Without a daemon-side tokio::time::interval that scans `pending_expiring_executions` periodically, "terminates within its TTL" is operator-dependent, not type-level. This is the single largest gap.
2. Crash safety. In `execute_quarantine_file_response`, `fs::rename` runs at api_server.rs:11260 BEFORE the ledger append at api_server.rs:11270 (via `append_and_receipt_edr_response_execution`). If the agent crashes between rename and ledger append, the side effect is live on disk with no execution record - the rollback path has no execution_id to operate on. Same race in disable_persistence (11347 vs 11357). For process signals (suspend/terminate), the signal delivery (11460, 11521) similarly precedes the ledger append (11482, 11539). A write-ahead pattern (append a "pending" record before the side effect, then mark "succeeded" after) would close this.
3. Quorum-required mode. No cosignature requirement is wired. `grep` for cosign / quorum / two_signer / second_signature / dual_control across edr.rs and api_server.rs returns zero hits. Destructive actions (TerminateProcessTree, RevokeGrant) execute on a single endpoint-side keypair signature with no operator co-signature.
4. Bilateral acknowledgement. `EndpointResponseAcknowledgementReport` (edr.rs:4278) is signed only by the endpoint keypair (api_server.rs:20853, same single keypair as everything else). The optional `control_correlation` (edr.rs:4250) records `ack_token_hash` but does not carry a second signature. A "device + operator both signing" model is not present.
5. Terminate is not actually reversible. SIGTERM was sent at api_server.rs:11521; the receipt carries an `effect_type: "terminate_process_tree"` (edr.rs:3142) but there is no rollback constructor in `EndpointResponseRollbackReport` and no `execute_terminate_process_tree_rollback`. The rollback router at api_server.rs:18293-18306 explicitly excludes it. The theorem text says "carries a rollback receipt closing it" - terminate cannot satisfy this; it would have to be classified as quorum-required-only or as a different action class.
6. Revoke-grant similarly has no rollback. Token rotation, broker capability revocation, and SIEM API key revocation are one-way under the current code.
7. SensorState fidelity on rollback receipts. As noted above, only the execution receipt carries real sensor state; the rollback/acknowledgement/plan receipts use `single_active_agent` placeholder. A theorem stating "rollback receipts faithfully attest sensor posture at rollback time" cannot hold today.
8. Race condition between concurrent manual-rollback and TTL-driven rollback. No per-execution lock; the same rollback function runs from both paths. The egress ledger has a mutex (api_server.rs:11551), but quarantine/disable_persistence depend on `rename(2)` atomicity plus a `target_path.exists()` precheck that is TOCTOU-racy.
9. No verifier-side check that rollback receipts strictly invert the execution receipt's effects. The `restrict_egress` constructor (edr.rs:3967-3973) and `suspend_process_tree` constructor (edr.rs:4173-4179) self-check content_hash/byte_count parity; quarantine_file and disable_persistence rollback constructors do not run a similar inverse-content-hash check on the artifact (the runtime executor at api_server.rs:11646-11653 does, but a verifier consuming only the receipt pair cannot infer this).

## Bottom line

The response engine is real and the executors are real - six action variants have actual OS side effects (rename, SIGSTOP, SIGCONT, SIGTERM, broker revocation, NE policy reload), and the corresponding rollback functions for four of them are inverse-by-construction with content-hash gates on the file paths and pid sets. Test coverage spawns real processes and writes real files, not just JSON round-trips. What the code does NOT do today: there is no background TTL reaper (the `/expire` endpoint is HTTP-trigger only with no scheduler), execution-record persistence happens AFTER the side effect runs (crash window between effect and ledger), three of the seven executors (Terminate, RevokeGrant, CollectEvidence) have no rollback path, and there is no operator cosignature for destructive actions - every receipt is signed by a single endpoint Ed25519 keypair. For the bounded-executive-action paper to cite this code as the empirical chapter, the honest framing is "rollback receipts and per-action executors are implemented for four actions; TTL is encoded but not autonomously enforced; quorum-required mode does not exist." Closing the TTL-reaper gap and adopting write-ahead ledger semantics would land the empirical claim. Without that, the theorem as stated ("terminates within its TTL OR carries a rollback receipt") is not falsifiable against this binary, because the disjunct's left arm is operator-dependent.
