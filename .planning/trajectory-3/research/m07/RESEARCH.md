## C-ABI surface design

The existing crate already commits to the C-ABI shape via UniFFI: a thin
`extern "C"` shim generated by `build.rs` from
`src/chio_kernel_mobile.udl`. UniFFI's wire format is its own binary
encoding (LEB128 varints + length-prefixed strings) which is opaque to
the consumer; Swift / Kotlin call into the generated bindings as if
they were native methods.

**Why JSON-in / JSON-out at the function boundary** (per the in-tree
comment): Chio's type graph (CapabilityToken, ChioScope, ChioReceiptBody,
PortablePassportEnvelope) has 40+ fields with deeply nested structs.
Restating that graph in UDL would double the FFI surface for zero safety
gain because the app-side Chio SDK already serializes these types via
serde. The decision is to marshal once via JSON at the boundary and keep
UDL minimal (4 fns, 2 records, 1 error enum).

**Sister kernels for reference:**

- `crates/chio-bindings-ffi/src/lib.rs` (556 LOC): plain C ABI used by
  the desktop / hosted-oracle FFI consumer. Exposes `chio_buffer_free`,
  `chio_ffi_abi_version`, `chio_canonicalize_json`,
  `chio_sha256_hex_*`, `chio_sign_*`, `chio_verify_*`,
  `chio_verify_capability_json`, `chio_verify_receipt_json`,
  `chio_verify_manifest_json`. Uses `ChioFfiBuffer` + `ChioFfiResult`
  status structs; 18 `#[no_mangle]` symbols.
- `crates/chio-cpp-kernel-ffi/src/lib.rs` (727 LOC): plain C ABI for
  the C++ offline kernel package. Mirrors the mobile adapter's
  JSON-in / JSON-out shape but uses raw C ABI (no UniFFI). Status /
  error code constants (`CHIO_KERNEL_FFI_STATUS_OK = 0`, etc.). Six
  `#[no_mangle]` exported functions:
  `chio_kernel_ffi_abi_version`, `chio_kernel_build_info`,
  `chio_kernel_buffer_free`, `chio_kernel_evaluate_json`,
  `chio_kernel_sign_receipt_json`, `chio_kernel_verify_capability_json`,
  `chio_kernel_verify_passport_json`.

The C-ABI surface for mobile is **a subset of `chio-cpp-kernel-ffi`'s**
JSON-in / JSON-out functions, projected through UniFFI rather than raw
C. The two surfaces should be kept symmetric so a single behavioral
test corpus exercises both. M07's P1 cross-platform parity test (per
the narrative's risk #2) should drive the same JSON fixture through
the Rust-side `evaluate()` and the C++ `chio_kernel_evaluate_json` and
assert byte-equal verdicts.

**Serialization choice:** JSON is the right answer for M07 even though
FlatBuffers / MessagePack are smaller. Reasons:

1. The Chio type graph already has serde Serialize/Deserialize impls
   that produce canonical JSON consistent with the receipt-signing
   pipeline (`canonical_json_bytes`).
2. Mobile callers debug crashes with print-the-JSON; binary formats
   make that worse.
3. Bandwidth is not a constraint at the FFI boundary (in-process call;
   no network).
4. The hosted oracle (M01 P3 / P4) speaks JSON receipts; the mobile
   adapter must produce wire-compatible output without re-serialization.

**Recommendation for M07 P1:** preserve the JSON-in / JSON-out UDL
shape; do NOT introduce FlatBuffers or MessagePack. Add the App Attest
/ Play Integrity entry points as additional UDL functions:

- `attest_app_attest(key_id, challenge_hex) -> AppAttestEvidence`
- `attest_play_integrity(nonce_hex) -> PlayIntegrityEvidence`
- `verify_mobile_receipt(receipt_json, evidence_json) -> VerifiedMobileReceipt`

These three functions are the new C-ABI surface entries for M07. With
the four existing entries, the **C-ABI surface count is 7**, which the
P0 audit doc should record.

## iOS framework + Swift Package research

**Packaging choice: XCFramework + Swift Package Manager (SPM).**

Reasons:

- Apple's binary-shim requirements: SPM binary targets distributed as
  XCFramework are the only Apple-blessed path for shipping a closed-
  source binary that supports both device + simulator + Mac Catalyst
  in a single artifact. CocoaPods is on the way out (the CocoaPods
  team announced the project's wind-down in 2024); new vendors should
  default to SPM.
- The existing `bindings/README.md` already commits to the
  `xcodebuild -create-xcframework` workflow that lipos
  `aarch64-apple-ios`, `aarch64-apple-ios-sim`, and `x86_64-apple-ios`
  static libraries.
- SPM XCFrameworks integrate with the App Store Connect signing flow
  without bridging headers; the `out/swift/chio_kernel_mobileFFI.h`
  header bundles into the XCFramework.

**Minimum iOS version:** App Attest requires iOS 14.0+. SPM binary
target requires Swift 5.3+ (Xcode 12.5+). The conservative pin is
**iOS 15.0** (matches Apple's current minimum-supported deployment
target as of Xcode 15+; iOS 14 is past Apple's typical 3-version
support window). The P0 audit doc should record "minimum iOS API
level pinned: 15.0".

**Layout proposal under `sdks/swift/`:**

```
sdks/swift/
  Package.swift                      # SPM manifest with binary target
  Sources/
    Chio/                            # Public Swift surface
      Chio.swift                     # Re-exports + ergonomic wrappers
      AppAttest.swift                # DCAppAttestService integration
      Keystore.swift                 # Keychain + Secure Enclave wrap
    ChioFFI/                         # UniFFI-generated module
      chio_kernel_mobile.swift
      chio_kernel_mobileFFI.h
      module.modulemap
  Tests/
    ChioTests/                       # XCTest harness
  Frameworks/
    ChioKernel.xcframework/          # Output of xcodebuild -create-xcframework
  README.md
```

**Build pipeline:** repo-local `scripts/build-ios-framework.sh` builds
the three iOS targets via `cargo build --target ... -p
chio-kernel-mobile` then runs `uniffi-bindgen generate --language swift`
and `xcodebuild -create-xcframework`. The script writes its qualified
output under `target/release-qualification/mobile-kernel/ios/`.

**Open question for IMPLEMENT:** does Backbay want to publish the

under the `m07-kernel-mobile-pivot` distribution? The narrative says

## Android AAR + Gradle research

**Packaging choice: prebuilt AAR consumed via a Gradle Maven repo.**

Reasons:

- AAR is the standard Android library distribution format. It bundles
  `classes.jar`, `jniLibs/<abi>/libchio_kernel_mobile.so` for each ABI,
  and the `AndroidManifest.xml` shim.
- A custom Gradle plugin would force the consumer to pin a plugin
  version on top of an AAR version, which is more friction than
  benefit at MVP scale.
- Per `bindings/README.md`, the existing build pipeline uses
  `cargo ndk` to cross-compile to `aarch64-linux-android`,
  `armv7-linux-androideabi`, `x86_64-linux-android`, and
  `i686-linux-android`. Those `.so` artifacts go directly into the
  AAR's `jniLibs/`.

**JNI bridge:** UniFFI-generated Kotlin bindings use **JNA** (Java
Native Access; `net.java.dev.jna:jna:5.14.0@aar`). JNA loads the
shared library at runtime; the consumer does not write JNI code.
This is the upstream UniFFI convention.

**Minimum Android API:** Play Integrity requires API 21 (Lollipop)+.
StrongBox-backed Keystore requires API 28 (Pie)+ AND device hardware
support. App Attest's analogue (hardware-backed keystore via
`KeyGenParameterSpec.setIsStrongBoxBacked(true)`) requires API 28 with
fallback to TEE on API 23+. The conservative pin matches the iOS
choice in spirit: **API 26 (Android 8.0)** for the Chio SDK floor with
a soft requirement of API 28 for hardware-backed attestation. Devices
on API 26-27 fall back to software attestation with a degraded
trust-level marker on the issued capability.

**Layout proposal under `sdks/kotlin/` (or `sdks/jvm/` since the
existing tree has `sdks/jvm/`; recommend `sdks/jvm/chio-kernel-mobile/`
to share the existing JVM lane):**

```
sdks/jvm/chio-kernel-mobile/
  build.gradle.kts                   # AAR module config
  settings.gradle.kts
  src/main/
    kotlin/dev/chio/kernel/
      Chio.kt                        # Public Kotlin surface
      PlayIntegrity.kt               # IntegrityManager wrapper
      Keystore.kt                    # AndroidKeystore + StrongBox wrap
    java/uniffi/chio_kernel_mobile/
      chio_kernel_mobile.kt          # UniFFI-generated
    jniLibs/
      arm64-v8a/libchio_kernel_mobile.so
      armeabi-v7a/libchio_kernel_mobile.so
      x86_64/libchio_kernel_mobile.so
      x86/libchio_kernel_mobile.so
  src/test/
  src/androidTest/
  README.md
```

**Build pipeline:** `scripts/build-android-aar.sh` runs `cargo ndk`
plus `uniffi-bindgen generate --language kotlin` plus `./gradlew
:chio-kernel-mobile:assembleRelease`. Output AAR lands at
`sdks/jvm/chio-kernel-mobile/build/outputs/aar/chio-kernel-mobile-release.aar`.

**Distribution:** publish to GitHub Packages Maven (private) for the
internal Opus mobile patient-app consumer; defer Maven Central
publication.

## Apple App Attest integration

**API: `DCAppAttestService` (DeviceCheck framework).** Available
iOS 14.0+. The integration is a four-step issuance flow:

1. **Generate a key.** Call `DCAppAttestService.shared.generateKey
   { keyId, error in ... }`. The service returns an opaque key
   identifier; the actual private key is stored in the Secure Enclave
   and never exposed to the app.
2. **Attest the key.** Call `DCAppAttestService.shared.attestKey(
   keyId, clientDataHash: hash) { attestation, error in ... }` where
   `clientDataHash` is the SHA-256 of a server-issued challenge. The
   service returns a CBOR-encoded attestation containing the device's
   anonymous identifier, the hardware-backed public key, and a chain
   of certificates rooted in Apple's App Attest root CA.
3. **Server verification.** The Chio issuer (the kernel-side oracle
   in `crates/chio-custody-hw/src/attestation/`) verifies the
   attestation chain against Apple's App Attest root CA, asserts the
   App ID matches the expected bundle, and binds the resulting public
   key to the user's tenant.
4. **Per-call assertions.** For each subsequent capability mint or
   sensitive call, the app calls `DCAppAttestService.shared.generateAssertion(
   keyId, clientDataHash: ...)` and forwards the assertion to the
   issuer; the issuer verifies the signature against the previously-
   attested key.

**Minimum integration for the MVP:** the kernel-side oracle needs to
implement the verification half of steps 3 + 4. The mobile-side app
runs steps 1, 2, and 4 directly via Apple's framework. The kernel
keypair binding is **the kernel sees the App Attest public key as the
mobile device's authentication credential**; capabilities are minted
audience-pinned to that key.

**Verification literature:**

- Apple "Establishing your app's integrity" (DeviceCheck framework
  developer docs).
- RFC 9421 (HTTP Message Signatures) is NOT App Attest's wire format;
  App Attest uses Apple's CBOR encoding documented in "Validating
  Apps That Connect to Your Server".
- Apple App Attest root CA fingerprint is documented in Apple's
  developer portal; pin it in `crates/chio-custody-hw/src/attestation/
  apple_root.rs` (new file).

**Implementation surface in `crates/chio-custody-hw/src/attestation/`:**

```
attestation/
  mod.rs                  # Public surface
  app_attest.rs           # Apple App Attest verification
  apple_root.rs           # Pinned Apple root CA + intermediate
  play_integrity.rs       # Android Play Integrity verification
  google_root.rs          # Pinned Google attestation root
  receipt_chain.rs        # Cross-platform receipt validation
  errors.rs
```

**External evidence:** the verdict notes App Attest issuance IS the
third-party evidence. Concretely, what M07 records as evidence is:

- Apple Developer account `@bb-connor` (per narrative TODO) registered
  for the app bundle id.
- A test attestation issued by the App Attest service against a
  real iOS binary in TestFlight.
- The CBOR attestation blob committed under `crates/chio-custody-hw/
  tests/fixtures/app_attest/` as a recorded fixture.

## Android Play Integrity integration

**API: `IntegrityManager` (Play Integrity API, `com.google.android.
play:integrity`).** Replaced SafetyNet, which Google deprecated in 2024.

Three-step issuance flow:

1. **Request integrity verdict.** App calls
   `IntegrityManager.requestIntegrityToken(IntegrityTokenRequest
   .builder().setNonce(serverNonce).build())`. The service returns a
   JWS-signed token containing `appIntegrity`, `deviceIntegrity`,
   and `accountDetails` claims.
2. **Server verification.** The Chio issuer decrypts the token using
   the server-side key from the Google Play Console (or uses Google's
   Standard API for verification by Google's servers); validates the
   `appIntegrity.appRecognitionVerdict == "PLAY_RECOGNIZED"`,
   `deviceIntegrity.deviceRecognitionVerdict` contains
   `"MEETS_DEVICE_INTEGRITY"`, and the nonce matches.
3. **Hardware-backed key issuance.** Separately, the app generates a
   key in the Android Keystore with
   `KeyGenParameterSpec.Builder(...).setIsStrongBoxBacked(true)` (API 28+;
   fall back to TEE on API 23-27). The Keystore exposes a key
   attestation certificate chain rooted in Google's hardware
   attestation root; the issuer verifies that chain to confirm the
   key is hardware-backed.

**Issuance flow:** the issuer's mint endpoint accepts both the Play
Integrity token (authentication-of-app) AND the keystore attestation
chain (authentication-of-key) in a single mint request. The issued
capability is audience-pinned to the StrongBox key. This mirrors the
App Attest flow's decoupling of "the device + app are real" from
"this is the persistent key bound to that device".

**Verification literature:**

- Google Play Integrity API docs (`developer.android.com/google/
  play/integrity`).
- Android Keystore key attestation
  (`developer.android.com/training/articles/security-key-attestation`).
- The Keystore certificate chain is X.509 with Google's
  attestation root; pin the root in
  `crates/chio-custody-hw/src/attestation/google_root.rs`.

**Library choice on Android:** use Google's official Play Integrity
client library (`com.google.android.play:integrity:1.3.0`+) and
Android Keystore directly. Do NOT add a third-party wrapper; the
surface is small enough to call via JNI / Kotlin.

**External evidence:** Google Play Console account `@bb-connor`
registered for the app package id. A test integrity verdict issued
against the internal-track APK; the JWS payload committed under
`crates/chio-custody-hw/tests/fixtures/play_integrity/`.

## Hardware-attestation keystore (vs PasskeyCapability)

**Question:** how do iOS Secure Enclave keys + Android StrongBox keys
differ from the trajectory-2 M10 PasskeyCapability surface? Are they
the same surface or different?

**Answer: different surfaces, complementary roles.**

trajectory-2 M10 PasskeyCapability (`crates/chio-custody-hw/`,
`sdks/typescript/packages/passkey/`):

- **Authn factor:** WebAuthn passkey. The browser presents an
  assertion to the server; the server mints a capability.
- **Key location:** platform authenticator (Touch ID, security key,
  Windows Hello, etc.).
- **Issuer signs:** the server (the issuer uses the trajectory-2
  M03 HybridBackend to sign the audience-pinned capability).
- **Browser holds:** zero key material. The capability is opaque.
- **Trust model:** "this user proved possession of the passkey at
  mint time" plus "this capability is audience-pinned to the
  caller domain".

trajectory-3 M07 mobile attestation (`crates/chio-kernel-mobile/`,
`crates/chio-custody-hw/src/attestation/`):

- **Authn factor:** App Attest (iOS) or Play Integrity (Android) plus
  hardware-backed Keystore key.
- **Key location:** Secure Enclave (iOS) or StrongBox / TEE (Android).
- **Issuer signs:** the server, same as M10. The mobile flow extends
  the issuer with App Attest / Play Integrity verification on top of
  the existing audience-pinned mint pipeline.
- **Mobile holds:** zero exportable key material. The hardware-backed
  key is referenced by an opaque key id; the OS performs the signing
  on demand.
- **Trust model:** "this device + app pair is real per Apple/Google"
  plus "this key is hardware-backed and bound to the device" plus
  "this capability is audience-pinned".

**Surface decision for M07:** extend `chio-custody-hw`'s issuer with
mobile attestation chain handling (the new `attestation/` submodule)
rather than fork a new crate. The mint pipeline gains two new accepted
authn factors (App Attest + Play Integrity) alongside the existing
WebAuthn passkey factor. The issued capability is the same shape; the
trust-level marker on the capability records which factor authenticated
the mint.

**Coordination with M10 (trajectory-2):** M10 of trajectory-2 owns
`chio-custody-hw` as the home for hardware-backed authn. M07 of
trajectory-3 extends that crate without replacing it. The
`m07-kernel-mobile-pivot` freeze covers
`crates/chio-custody-hw/src/attestation/**` (a path that does not yet
exist on `main`) precisely so the M07 milestone can author it
under its own freeze without colliding with trajectory-2 carry-forward
work.

## Chiodome step-toward framing

The verdict notes M07 is "the load-bearing Chiodome step (citizens
carry credentials, not server fleets)". Concretely:

- **Chiodome thesis:** an agent swarm congregates as digital fiscal
  nation states; citizens (humans + agents) carry portable, hardware-
  attested credentials.
- **What M07 ships toward that thesis:** a credential bound to the
  citizen's device hardware (Secure Enclave / StrongBox), attested
  by the platform vendor (Apple / Google), and audience-pinned by
  the Chio issuer. The citizen's mobile device becomes the
  **credential carrier** rather than a server fleet's authentication
  proxy.
- **Why this is the load-bearing step:** without M07, every Chio
  citizen is tied to a server-side session. With M07, a citizen's
  device IS the authentication factor; the server fleet validates
  but does not custody. This inverts the trust relationship from
  "server vouches for user" to "user's hardware vouches for itself,
  server validates the hardware".
- **Trajectory-3 framing:** M07's narrative should explicitly say
  "this is the first Chiodome-shaped milestone: credentials live in
  citizen hardware, not server fleets". Future Chiodome milestones
  (cross-device sync, social recovery, multi-citizen quorum) build on
  this foundation.

The narrative doc currently does not name Chiodome; the IMPLEMENT
phase should add a one-paragraph "Chiodome step-toward" section under
"Why this is on the trajectory" (or as its own section) so the
Chiodome connection is explicit in the milestone artifact, not just
in the user's auto-memory.

## Risk register

Risks consolidated from the narrative + research; each carries a
mitigation. Numbering continues from the narrative's existing risks
1-3.

1. **App Attest / Play Integrity API changes mid-cycle.**
   *Narrative risk 1.* Mitigation: pin SDK versions
   (`com.google.android.play:integrity:1.3.0`+); nightly canary against
   published API docs; CI fails on signature drift.

2. **C-ABI surface drift across platforms.** *Narrative risk 2.*
   Mitigation: P1 cross-platform parity test runs the same JSON corpus
   through Swift and Kotlin bindings AND the C++ FFI; asserts byte-
   equal verdicts.

3. **App Store / Play Store review delays the mobile demo.**
   *Narrative risk 3.* Mitigation: M07 ships ad-hoc / TestFlight /
   internal-track first; production-store listing is out of scope.

4. **Hardware-attestation availability on older devices.**
   StrongBox requires API 28 + device hardware support; the iPhone 8
   (iOS 14 cutoff) is the floor for App Attest. Mitigation: the
   issuer accepts software-attested capabilities with a degraded
   trust-level marker; the patient-app gates sensitive flows on the
   `trust_level == hardware` predicate. P0 audit doc records the
   degradation policy.

5. **Cross-platform receipt format drift.** Mobile receipts must be
   wire-compatible with the M01 hosted-oracle schema. Mitigation: the
   Rust-side `sign_receipt()` already uses `chio-kernel-core`'s
   canonical-JSON pipeline shared with the desktop and browser
   kernels; P4 adds an end-to-end test that posts a mobile receipt
   to a fixture oracle and asserts schema acceptance.

6. **UniFFI version churn.** UniFFI 0.28 -> 0.29+ has historically
   changed wire encoding; bumping breaks every consumer. Mitigation:
   pin to 0.28.3 in `Cargo.toml`; document the upgrade path; defer
   upgrades to a dedicated trajectory-4 ticket.

7. **Apple Developer / Google Play Console account onboarding.**
   The bindings require platform-vendor accounts under `@bb-connor`'s
   ownership. Mitigation: P0 audit doc fill captures the account IDs;
   if accounts are not provisioned by week 2, escalate to the
   trajectory orchestrator's halt-trigger 11 (vendor-blocking).

8. **Expo dev-client compatibility breakage.** Expo SDK 50 / 51
   transitions can break native modules. Mitigation: the RN bridge is
   a stub, not a polished package; pin Expo SDK and document the
   matrix in the M07 audit doc.

9. **NDK toolchain dependency on operator hosts.** `cargo ndk`
   requires Android NDK r25+. Mitigation: `qualify-mobile-kernel.sh`
   already records `environment_dependent` lanes honestly; CI runs on
   a host with the toolchain pre-provisioned.
