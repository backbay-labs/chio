# T1.3 - Anchor-batch Merkle trees with public-witness checkpoints

**Status**: pending. **Owner**: TBD (protocol eng lead).

**Tickets**: TRJ4-140 through TRJ4-147, plus `TRJ4-T1.3.E` Evidence Gate.

## Scope

Two-way consensus from the brainstorm (perf-scale + protocol-evolution). Build a Merkle tree over N receipts/checkpoints; sign once; attach inclusion proof per element; publish root to a public witness lane.

**Framing (round-3 + round-4 reviewer corrections)**: this is **additive** over per-receipt signing, not a replacement. The immediate local receipt remains independently verifiable. The batch root upgrades continuity (the batch attests N receipts as a set) and non-repudiation (the witness lane gives third-party timestamping). The artifact alone **moves toward closure** of the `audit_only` / `transparency_preview` ceiling at PROTOCOL.md:657, but does not by itself close it. Closure requires the Evidence Gate items below.

## Acceptance

1. **`chio.anchor_batch.v1` schema and signer** (TRJ4-140): `{tree_root, checkpoint_ids[], witness: rekor|ots|solana_memo}` artifact authored at `spec/schemas/chio-wire/v1/anchor/batch.schema.json`.
2. **Coalesced batch root** (TRJ4-141): build a Merkle tree over N receipts/checkpoints; attach inclusion proof per element. Mirrors the existing `chio-anchor` checkpoint Merkle batching at `crates/chio-anchor/src/lib.rs:113-144`.
3. **Per-receipt local sign stays unchanged** (TRJ4-142): the batch issuance lane is non-blocking on the receipt write path. Local receipts remain verifiable without the batch.
4. **Witness lane: Rekor** (TRJ4-143): publish batch root to a Rekor instance; verify inclusion via Rekor `getEntryByUUID` on read.
5. **Witness lane: OTS** (TRJ4-144): operational alternative to Rekor; OpenTimestamps publish + verify.
6. **Claim registry update** (TRJ4-145): `chio.anchor_batch.v1` registered with its claim shape.
7. **Proof manifest update** (TRJ4-146): tied to the Merkle-inclusion verification path.
8. **Public-witness semantics doc** (TRJ4-147) at `docs/security/public-witness-semantics.md`:
   - Anti-equivocation guarantee (a batch root cannot be re-signed under a different content set after publication).
   - Claim-completeness guarantee (every checkpoint in the batch is named in `checkpoint_ids[]`).
   - Stale-witness fallback policy: when a witness lane (Rekor / OTS / Solana memo) is unavailable for > N minutes, what does that imply for receipts in the batch? Documented behavior: receipts remain locally valid; batch-level continuity claim degrades to "pending public witness" rather than failing the receipt.

## Evidence Gate (TRJ4-T1.3.E)

Closes only when:

- `spec/PROTOCOL.md` updated with `chio.anchor_batch.v1` semantics and the additive-over-per-receipt framing.
- `spec/schemas/chio-wire/v1/anchor/batch.schema.json` committed.
- Claim registry entry merged.
- Proof manifest updated.
- Theorem inventory updated (Merkle inclusion verification, public-witness anti-equivocation theorem).
- Generated proof report regenerated.
- Public-witness semantics doc committed.
- Negative conformance tests:
  - **Forged batch root**: batch claiming to contain checkpoint X but X's inclusion proof does not verify against the root - fails closed.
  - **Mis-ordered inclusion proof**: tampered Merkle path - fails closed.
  - **Witness-lane impersonation**: batch claims Rekor witness but the entry under that UUID is a different root - fails closed.
  - **Stale-witness fallback**: when the Rekor instance is unreachable, receipts in the batch remain locally verifiable; a verifier configured with `require_public_witness: true` rejects new batches but accepts already-witnessed ones.

## Evidence to capture

- End-to-end: 1000 receipts batched, root published to Rekor staging, inclusion proofs verified for sample of 100.
- Same 1000 receipts batched again with one tampered inclusion proof - tampered receipt rejected.
- Witness-lane interoperability: batches witnessed in Rekor verifiable from clients using OTS-only verifier (the verifier should fail closed when witness lane mismatches its allow-list, but should NOT corrupt local-receipt validity).

## Risks / open questions

- Rekor staging instance availability for CI; document fallback to mock-Rekor for offline tests.
- OTS confirmation latency (~10 min for Bitcoin block) means the test loop has to mock OTS for fast CI; real-time validation runs in nightly.
- Solana memo lane is stretch; Rekor + OTS satisfy the minimum.
