# T1.6 - `chio explain <receipt-id>` CLI

**Status**: implemented in Lane C PR #576. **Owner**: DX / CLI.

**Tickets**: TRJ4-180 through TRJ4-183.

## Scope

A receipt-narrator CLI that walks the policy decision and renders human-readable rationale. CLI only; the full web explorer is T3.10 stretch.

T1.6 sits in T1 because it makes the new receipt-DAG (T1.2), attenuation chain (T1.1), and batch witness (T1.3) **legible while the team is still building them**. Without it, debugging T1.1/T1.2/T1.3 is a JSON-grep exercise.

## Acceptance

1. **`chio explain <receipt-id>` accepts both shapes** (TRJ4-180):
   - Legacy UUIDv7 (e.g. `rcpt_01H...`) - resolved through the alias index from T1.2.
   - v2 `body_hash` (hex) - resolved direct.
   - Ambiguous prefixes prompt for clarification rather than guessing.
2. **Render policy + guard rationale** (TRJ4-181):
   - Which policy clause matched (or which clauses were checked and rejected).
   - Which guards fired and their per-guard verdict.
   - Scope diff: the requested scope vs the granted scope, with widenings highlighted.
   - Parent receipt(s) for the DAG (one or many, after T1.2).
   - Batch witness lane (after T1.3) with link to the witness UUID.
   - Repair hint if denied (e.g., "missing capability `tool.fs.write`; mint with `chio mint --add-capability tool.fs.write`").
3. **Render attenuation chain** (TRJ4-182):
   - Parent capability -> child capability with each `Caveat` shown as a row.
   - `attenuation_proof` witness presented at each hop with `parent_scope_hash`, `child_scope_hash`, normalized subset relation.
   - Subset-of-parent assertion with pass/fail marker.
4. **"Why was this called?" trace** (TRJ4-183):
   - Walk the receipt DAG: `user_msg -> plan_id -> sub_agent_id -> tool_call_id`.
   - Render as a tree with edge annotations.
   - Pairs with the AI-frontier A-12 brainstorm.

## Evidence to capture

- Snapshot tests of the CLI output for: simple Allow, simple Deny with repair hint, multi-hop attenuation chain, fan-out DAG with three siblings.
- CLI works against a v1 legacy receipt, a v2 content-addressed receipt, and a cross-org delegation chain.
- Repair-hint accuracy: synthetic Deny test asserts the hint matches the actual missing capability.

## Risks / open questions

- Receipt-DAG rendering at scale (1000+ siblings) needs a sane truncation strategy with `--depth` and `--fanout-limit` flags.
- Repair-hint generation needs to know the relevant policy clauses; if `chio explain` only has the receipt and not the policy, it can show the gap but may not propose a specific mint command. Document this.
- Cross-org receipts may resolve through a federation peer's receipt store; CLI surface needs `--peer <did>` flag.
