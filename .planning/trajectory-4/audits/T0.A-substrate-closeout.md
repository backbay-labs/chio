## Release-tag policy (must ratify before TRJ4-002)

The plan and prior trj3 closeout posture used the placeholder `v3.18.1-trj3.1`. Ground-truth check on the trj4-planning branch shows the actual existing release tags are:

```
cpp/v0.1.0
v0.0.0-m03-probe
v0.1.0
```

So `v3.18.1` is a multi-major-version jump with no precedent. Before TRJ4-002 can fire `release-binaries.yml` etc., the operator must ratify the actual versioning intent. Three reasonable options:

1. **Continue v0.x cadence**: tag `v0.2.0-trj3.1`. Lowest surprise; matches existing tags.
2. **Bump to a substrate-major**: tag `v1.0.0-trj3.1` to mark "substrate is stable enough to claim a 1.0 line." Requires a separate decision about what 1.0 means.
3. **Adopt the prior plan's `v3.18.1-trj3.1`**: requires backfilling `v0.2..v3.17` tags or accepting a discontinuity. Document the rationale in this audit.

This audit closes only when one of (1)/(2)/(3) is chosen and `releases.toml` plus the SLSA / reproducible-build workflows are wired to whichever version string is canonical. TRJ4-002 references the chosen tag throughout (the EXECUTION-BOARD ticket placeholder `v<chosen-version>-trj3.1` is concretized when the policy lands).
