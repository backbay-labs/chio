# chio-guard-sdk architecture

## Overview

`chio-guard-sdk` is the guest side of the guard trust boundary: it compiles
into the WASM module the kernel sandboxes and evaluates, not into the kernel
itself. It owns the JSON ABI shared with the host (byte-compatible with the ABI
in `chio-wasm-guards`), the guest allocator the host writes requests through,
and the glue that turns a `GuardVerdict` into the host-visible return code and
deny reason. On `wasm32` every host wrapper calls the real import; on native
targets each one falls back to a no-op or a documented default so guard
decision logic runs under `cargo test` without a WASM runtime.

## Module map

| Path | Responsibility |
|------|----------------|
| `src/lib.rs` | Declares the four modules, re-exports the guard-author API at the crate root, and defines `prelude`. |
| `src/types.rs` | `GuardRequest`, `GuardVerdict`, `GuestDenyResponse`, the `VERDICT_ALLOW` / `VERDICT_DENY` constants, and deny-reason normalization. |
| `src/host.rs` | Raw `extern "C"` FFI declarations for the `chio` and `chio:guard/host@0.2.0` import modules (`wasm32` only), plus safe wrappers `log`, `get_config`, `get_time`, `fetch_blob`, and the `PolicyContext` handle. |
| `src/glue.rs` | `read_request` (deserializes from linear memory), `encode_verdict` (verdict to ABI return code), and the `chio_deny_reason` export, backed by thread-local deny-reason storage. |
| `src/alloc.rs` | `chio_alloc` / `chio_free` exports: a `Vec<u8>`-backed allocator that keeps guest buffers alive in thread-local storage until freed. |

## Guest-host request lifecycle

1. The host calls `chio_alloc` to reserve guest memory, writes the serialized
   `GuardRequest` JSON into it, then calls `evaluate(ptr, len)`.
2. `evaluate` (generated by `#[chio_guard]`, or written by hand) calls
   `read_request(ptr, len)` to deserialize the request.
3. Guard logic returns a `GuardVerdict`. `encode_verdict` maps `Allow` to
   `VERDICT_ALLOW` and clears any stored deny reason; it maps `Deny { reason }`
   to `VERDICT_DENY` and stores the normalized reason in thread-local state.
4. On a deny, the host calls `chio_deny_reason(buf_ptr, buf_len)`, which
   serializes the stored `GuestDenyResponse` into the host's buffer and returns
   the byte count written, or -1 if nothing is stored or the buffer is too
   small.
5. The host calls `chio_free` to release the request allocation.

## Invariants and failure modes

- `GuardRequest` serde field names and `default` / `skip_serializing_if`
  annotations must stay byte-identical to the host definition in
  `chio-wasm-guards/src/abi.rs`; a mismatch fails at deserialization time, not
  at compile time.
- `read_request` is `unsafe` but still rejects a non-positive `ptr` or a
  negative `len` before constructing a slice, so a malformed pointer/length
  pair fails closed with an error instead of causing undefined behavior.
- `GuardVerdict::deny` and `encode_verdict` normalize blank or whitespace-only
  reasons to `DEFAULT_DENY_REASON` ("guard denied request"); a guard can never
  emit a deny with an empty reason string.
- `chio_alloc` returns 0 for `size <= 0`. `chio_free` is a silent no-op for a
  pointer/size pair that does not match a tracked allocation, rather than
  panicking on a double free or an invalid pointer.
- On non-`wasm32` targets, `log` is a no-op, `get_config` always returns `None`,
  `get_time` always returns 0, and `fetch_blob` always returns
  `Err("host.fetch-blob is unavailable on native targets")`.
- `PolicyContext::close` has no destructor import to call; the host stays
  responsible for reclaiming bundle resources after guard evaluation.

## Dependencies

External only: `serde` and `serde_json` for the ABI JSON shape. The crate has
no internal `chio-*` dependency, so it builds standalone for
`wasm32-unknown-unknown` guest targets without pulling in kernel or protocol
crates.

## Extension points

`chio-guard-sdk-macros` generates the `evaluate` export plus re-exports of
`chio_alloc`, `chio_free`, and `chio_deny_reason` around a plain
`fn evaluate(req: GuardRequest) -> GuardVerdict`. The macro crate has no
compile-time dependency on this crate; it emits code that references
`chio_guard_sdk::*` paths, resolved at the guard's own call site.
