# Durable Dispatch-Intent Journal Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the effect-before-receipt crash window (F04, F31; groundwork for F70 owned by RFC-0013) by writing a durable `chio_dispatch_intents` row through RFC-0006's single-writer actor before any side-effecting or monetary mediated call dispatches, and consuming that row in the same writer transaction that commits the receipt, so after any crash `receipt(request_id) XOR open_intent(request_id)` holds and orphans surface as loud dead-letter incidents.

**Architecture:** On the store side (`crates/platform/chio-store-sqlite`), a new non-audit `chio_dispatch_intents` table sits beside `chio_tool_receipts`; the pre-dispatch INSERT and the money-path rail-ref UPDATE ride RFC-0006's `WriterHandle::run_write` (metadata-only jobs on the single writer connection), and the same-transaction CONSUME (`DELETE` intent + `INSERT` receipt) mirrors `append_chio_receipt_consuming_authorization` exactly, running inside one `TransactionBehavior::Immediate` transaction via `run_write_receipt`. On the kernel side (`crates/kernel/chio-kernel`), a class gate writes the intent after the budget hold and before the earliest effect (prepaid `authorize`); an intent-write failure reverses every pre-execution hold through the existing pre-dispatch unwind (`build_pre_dispatch_cleanup_deny_response`) and denies before dispatch. Boot reconciliation dead-letters orphans into an operator-visible, health-flipping incident.

**Tech Stack:** Rust workspace crates `chio-store-sqlite` (rusqlite 0.33 via r2d2/r2d2_sqlite reader+writer pools; the RFC-0006 group-commit writer actor over `std::sync::mpsc`; `ReceiptCommitCommand::{Append,Flush,Write,ReseedHead,InstallSigner}`; `WriterHandle::{run_write,run_write_receipt}`; `VerifiedHead`), `chio-kernel` (`ReceiptStore` trait, `ReceiptStoreError`, `KernelConfig`, `KernelError`, `PreExecutionBudgetMutation`, `PostAdmissionDropGuard`, receipt-tenant request-scope), `chio-cli` (`clap` receipt health surface). Test infra already in the store crate dev-deps: `proptest`, `loom` (opt-in `chio_store_sqlite_loom` cfg), `tempfile`, `criterion`, `chio-test-support`; the kernel crate has `proptest` and an integration `tests/` dir.

### Anchor drift note (verified against the `chio/rfc-0006-storage` tree, 2026-07-08)

The RFC-0003 document was written against the pre-RFC-0006 tree; every anchor below was re-verified on this branch. Key moves and gaps the implementer must expect:

### Judgment calls (design deviations forced by grounding against RFC-0006)

- **JC-1 (writer routing):** the pre-dispatch intent INSERT and the money-path rail-ref UPDATE ride `WriterHandle::run_write` (metadata-only, `appends_receipts = false`); the same-transaction CONSUME rides `run_write_receipt` mirroring `append_chio_receipt_consuming_authorization`. This is NOT a new heterogeneous `Intent` batch command (the RFC's pre-RFC-0006 design, which cannot map onto RFC-0006's homogeneous append batch). The dispatch brief explicitly permits "a new writer command OR run_write job"; `run_write` is the idiomatic RFC-0006 primitive for a metadata-only single-writer job, and `store_checkpoint`/consuming-authorization already set the precedent. All journal writes stay on the single writer thread, satisfying the RFC's "written through the single-writer actor, NOT the reader pool" requirement.
- **JC-2 (read-only signal):** add a defaulted `fn tool_is_read_only(&self, _tool_name: &str) -> bool { false }` to `ToolServerConnection` (`runtime.rs:266`). Default `false` fails safe (unknown tool is treated as side-effecting and gets a durable intent, exactly the RFC's fail-safe). Adapters that know their annotations can override. The class gate is: `Monetary` if `has_monetary`; else `ReadOnly` if the connection reports read-only; else `SideEffecting`. This is the minimal in-tree bridge for the RFC's read-only optimization (F22 TTFRH), because `ToolAnnotations` is not otherwise reachable in the eval path.
- **JC-3 (intent-write-failure deny + Codex fix):** on an intent-write failure the eval path reverses every pre-execution hold through `build_pre_dispatch_cleanup_deny_response(PreDispatchCleanupDeny { .., payment_authorization: None, .. })`, the exact pre-dispatch unwind the admission-fail (`:439`) and authorize-fail (`:469`) arms use. This is STRICTLY MORE correct than the RFC's snippet (`unwind_aborted_monetary_invocation(request, cap, charge_result, None)`), which would leak an `Invocation`-kind budget hold and the sibling-sum capability admission (both live at the insertion point). `KernelError::DispatchIntentPersistence(String)` is the typed intent-write error whose message becomes the deny reason. This honors the RFC's Codex fix ("reverse the pre-execution budget hold, route through the pre-dispatch unwind, before denying, so a denied-before-dispatch call does not leak a budget hold").
- **JC-4 (consume plumbing):** the consume is driven by a request-keyed `Arc<DashMap<String, DispatchIntentHandle>>` on the kernel plus a thread-local fast path, mirroring the receipt-tenant scope EXACTLY (`receipt_tenant_ids` `kernel_struct.rs:235`; `scope_receipt_tenant_id_for_request` `construction.rs:68`; read by `build_and_sign_receipt` at `receipt_persistence.rs:22-23`). Because `ChioReceipt` has no `request_id` and the async eval future can migrate threads at the dispatch `.await`, the request-keyed map (not a bare thread-local) is the migration-safe primary, exactly as tenant resolution already is. The consume decision is centralized at the receipt-persistence sink so any terminal receipt kind (allow, post-dispatch deny, cancelled, incomplete) consumes the intent, never leaving a false orphan.
- **JC-5 (checkpoint drift):** RFC-0006 removed request-path checkpoint triggering, so the RFC's note about `append_chio_receipt_consuming_intent` returning `Option<u64>` "so the seq still drives `should_checkpoint_after_seq`" is moot on the kernel side. The method still returns `Result<Option<u64>, _>` for parity with `append_chio_receipt_returning_seq`; checkpoint construction is handled by the writer actor's post-job `build_due_checkpoints_and_record`, which the `run_write_receipt` path already invokes.
- **JC-6 (journal mode default):** `impl Default for DispatchIntentJournalMode` returns `SideEffecting` verbatim per the RFC's normative code block. The RFC's staged-rollout prose ("ship defaulting to Off in the first release") is a DEPLOYMENT decision expressed via `KernelConfig.dispatch_intent_journal`, not the compiled enum default.
- **JC-7 (rail id):** add a defaulted `fn rail_id(&self) -> &str { "payment" }` to `PaymentAdapter` (`payment.rs:150`) so the intent `rail` column can be populated for monetary calls; the trait has no existing id accessor. The X402 adapter may override with `"x402"`.

```rust
/// True if the non-audit `chio_dispatch_intents` journal table exists. A store
/// opened via `open_existing` on a pre-journal database runs no DDL, so a
/// missing table is reported as `false`; RFC-0003 callers treat that as zero

pub(crate) fn dispatch_intents_table_exists(
    connection: &rusqlite::Connection,

    let name: Option<String> = connection
        .query_row(
            "SELECT name FROM sqlite_master WHERE type = 'table' AND name = 'chio_dispatch_intents'",
            [],
            |row| row.get(0),
        )
        .optional()?;
    Ok(name.is_some())
}
```

```rust
            side_effect_class, monetary, rail, rail_authorization_id, tenant_id,
            created_at_unix_ms, state

        "#,
```

```rust
    pub fn reconcile_dispatch_intents(
        &self,
        reconciler: &dyn chio_kernel::receipt_store::DispatchIntentReconciler,
    ) -> Result<chio_kernel::receipt_store::DispatchIntentReconcileReport, ReceiptStoreError> {
        use chio_kernel::receipt_store::{DispatchIntentReconcileReport, DispatchIntentResolution};
        // Phase 1: read open intents off the reader pool.
        let open = {
            let connection = self.connection()?;
            crate::receipt_store::support::select_open_dispatch_intents(&connection)?
        };
        let mut report = DispatchIntentReconcileReport {
            open: open.len() as u64,
            ..DispatchIntentReconcileReport::default()
        };
        if open.is_empty() {
            return Ok(report);
        }
        // Phase 2: resolve on this thread (rail I/O, if any, never blocks the
        // single writer). Collect (request_id, detail) to apply.
        let mut resolutions: Vec<(String, String)> = Vec::with_capacity(open.len());
        for intent in &open {
            match reconciler.resolve(intent)? {
                DispatchIntentResolution::DeadLetter { detail } => {
                    report.dead_lettered += 1;
                    resolutions.push((intent.request_id.clone(), detail));
                }
                DispatchIntentResolution::MonetaryReconciled { rail_reference } => {
                    report.monetary_reconciled += 1;
                    resolutions.push((
                        intent.request_id.clone(),
                        format!("monetary reconciled; rail_reference={rail_reference}"),
                    ));
                }
                DispatchIntentResolution::SafeToReplay => {
                    // RFC-0003 default posture never returns SafeToReplay; if a
                    // future reconciler proves it, count it but leave the row open
                    // for the replay driver (out of scope here).
                    report.replayed += 1;
                }
            }
        }
        // Phase 3: apply the dead-letter/reconciled annotations on the writer.
        self.writer_handle().run_write(move |connection| {
            let tx =
                connection.transaction_with_behavior(rusqlite::TransactionBehavior::Immediate)?;
            for (request_id, detail) in &resolutions {
                crate::receipt_store::support::dead_letter_dispatch_intent_tx(
                    &tx, request_id, detail,
                )?;
            }
            tx.commit()?;
            Ok(())
        })?;
        Ok(report)
    }
```

```rust
            let _ = consume.join();
            let _ = drainer.join();

                0,
```
