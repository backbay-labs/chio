# Direction C: Governed x402 outbound rail (sim-first, custody-neutral) + anti-self-dealing guard

_Plan produced by the multi-wave agent team (research -> plan -> adversarial review). Status: DRAFT for maintainer approval._

**Review verdict:** needs-revision  |  **Effort:** v1 (M0-M4, one engineer): ~2-3 weeks. M1 anti-self-dealing is a ~2-3 day self-contained quick win that can land first and in parallel. M2 sim adapter + fail-closed gate ~2-4 days. M3 CLI/config productization ~3-5 days. M4 no-key smoke ~2-3 days. M5 (EIP-3009 ApprovalBinding bridge + off-chain settlement receipt) is a larger, schema-touching ~1-2 week body of work and is explicitly deferrable/optional for v1; ship Rail A alone if the EVM-binding-field source is not yet decided. Add ~0.5 day for the ADR-0015 status/governance change.

## Goal

Productize the governed outbound payment rail that already exists at the kernel (chio-kernel/src/payment.rs + validation.rs::authorize_payment_if_needed) into a shippable, deterministic, custody-neutral v1: a no-broadcast Sim facilitator adapter, a fail-closed "rail mandate present but no adapter => DENY" gate, a CLI/config surface to select the adapter, and a no-key CI smoke that proves a governed intent settles onto the signed tool-call receipt. In parallel, land ADR-0015 follow-up B (anti-self-dealing): constrain LiabilityClaimAdjudicationArtifact.adjudicator to an operator-supplied predeclared roster and record the applied decision-rule/circuit-breaker id, both enforced at every value-path boundary and both wire-compatible with existing signed fixtures. Optionally (deferrable) implement the documented GovernedApprovalToken -> ApprovalBinding seam so the orphaned chio-settle EIP-3009 prepare-only lane gains its first caller, staying digest-only (no broadcast). Reframe the premise: governed outbound x402/ACP-Client initiation + settlement-fold are NOT missing; what is missing is productization, a sim facilitator, fail-closed gating, and (for the on-chain-token lane only) the ApprovalBinding bridge.

## The real gap

Governed outbound x402 initiation is NOT one gap; it is a set of them, and one large piece the pointer implies is missing already exists:

Already present (correct the framing): governed outbound HTTP x402/ACP-Client authorization+capture is fully implemented at the kernel (payment.rs + validation.rs authorize_payment_if_needed L1227) and binds settlement onto the signed receipt (FinancialReceiptMetadata L1089-1108). The governed intent hash + approval token id are already forwarded to the rail.

Actually missing:
1. Productization: no product wires a real `PaymentAdapter` (set_payment_adapter only in tests). There is no CLI/config surface to choose/configure a facilitator, and no fail-closed policy forcing prepayment when a rail mandate is present but no adapter is configured (authorize_payment_if_needed returns None silently, validation.rs L1235).
2. Sim-first facilitator: no deterministic no-broadcast x402/ACP-Client sim facilitator/adapter exists (only ad-hoc test HTTP stubs). A "sim-first, custody-neutral" acceptance lane needs a stub facilitator (or the loopback devnet) plus a smoke.
3. GovernedApprovalToken -> ApprovalBinding bridge: the chio-settle EIP-3009 lane's `ApprovalBinding` (chain/payee/amount/token_contract) cannot be derived from the governed token/intent because the intent has no discrete EVM fields. The "seam" documented at payments.rs L177-189 has no implementation; the EIP-3009 lane has no caller at all.
4. Lane-specific settlement receipt for off-chain rails: the on-chain escrow lane has `Web3SettlementExecutionReceiptArtifact`; the HTTP x402 lane only stamps FinancialReceiptMetadata on the tool-call receipt; the EIP-3009 digest / Circle / paymaster lanes produce NO settlement receipt binding authorization_digest -> governed_receipt_id/execution_nonce.

Anti-self-dealing (cheap now): only the non-empty adjudicator check exists (claim.rs L319). Missing: (a) constrain `adjudicator` to a predeclared roster; (b) record the predeclared decision-rule / circuit-breaker condition id the adjudication applied (ADR-0015 follow-up B asks for BOTH; the pointer named only the roster). A roster type already exists (AdjudicationJurisdictionReceipt.adjudicator_subjects) but is in a different crate and not connected.

## Corrections to prior assumptions

- STALE/half-true: 'x402/rails: payments.rs already prepares approval-bound EIP-3009/x402 authorizations (verify-only projection today).' TRUE for chio-settle/payments.rs (prepare-only AND fully orphaned - no caller outside tests/docs). BUT the pointer misses that a REAL governed outbound x402/ACP-Client HTTP rail already exists at the kernel (chio-kernel/src/payment.rs X402PaymentAdapter/AcpPaymentAdapter), is wired into the guard/execution pipeline (validation.rs authorize_payment_if_needed L1227), and already binds settlement onto the signed receipt (FinancialReceiptMetadata L1089-1108) with the governed intent hash + approval token id forwarded to the facilitator. So 'take x402 from verify-only projection to governed outbound initiation' understates reality: initiation machinery exists; what is missing is productization (adapter only set in tests, construction.rs L429), a sim facilitator, and - for the EIP-3009 on-chain lane specifically - the GovernedApprovalToken->ApprovalBinding bridge and a lane-specific settlement receipt.
- REFINE: 'settlement receipt binds back to the authorization chain.' Only the on-chain escrow lane has a dedicated settlement receipt (Web3SettlementExecutionReceiptArtifact). The HTTP x402 lane binds via FinancialReceiptMetadata on the tool-call receipt. The EIP-3009 digest / Circle / paymaster lanes produce NO settlement receipt.
- ADD: ADR-0015 follow-up B asks for TWO things - constrain the adjudicator to a predeclared roster AND record the predeclared decision rule/circuit-breaker id applied (ADR L260-265). The pointer named only the roster.
- ADD: a predeclared adjudicator roster already exists as chio-trust-market-context AdjudicationJurisdictionReceipt.adjudicator_subjects (artifacts.rs L247); it is simply not connected to chio-market's adjudication. This makes 'cheap now' cheaper but introduces a cross-crate sourcing decision.
- PRECISE line numbers: adjudicator field is claim.rs L305 (as stated); the non-empty check that must be tightened is L319. sidecar.rs references belong to Direction A, not C.
- CONFIRMED: ADR-0015 Status is Proposed (not Accepted); ChioBondVault.impairBondDetailed (L124) lets the operator pick beneficiaries with no allowlist; the immutable-Solidity allowlist (follow-up A) is correctly deferred.
- CONFIRMED: custody-neutral is structurally supported for x402/EIP-3009/Circle/paymaster (all prepare/verify/facilitator-delegated, no fund-holding, no EIP-3009 broadcast in-tree). The ChioEscrow EVM lane really broadcasts via operator key but holds only the depositor's own funds in an admin-less contract - a distinct posture that should not be casually labeled the same 'custody-neutral' as the off-chain rails.

- M2: cargo test -p chio-kernel proves (a) a MustPrepay governed intent with no configured adapter is DENIED before execution (no silent Ok(None) fail-open), and (b) with SimPaymentAdapter the tool executes and the signed tool-call receipt's FinancialReceiptMetadata carries the deterministic sim payment_reference and a settlement_status in {Settled, Pending}; abort path unwinds via refund/release.

- ADR-0015 Status is Accepted (or explicitly Accepted-for-follow-up-B) with follow-up A (Solidity allowlist) recorded as deferred; the Rust roster + decision-rule constraints reference it as their normative anchor.
- M5 (only if landed): the chio-settle EIP-3009 prepare-only lane has its first non-test caller via the ApprovalBinding bridge, all existing fail-closed binding/nonce/window assertions still reject mismatches, and a new off-chain settlement receipt binds authorization_digest -> governed_receipt_id; still no in-tree broadcast.

GovernedTransactionIntent has none of these today (only max_amount + seller + shared_payment_token_id). Either extend the intent schema (wire/schema change) or introduce a seller->rail mapping/config resolved by the caller.
3. A sim target: either a deterministic no-key stub facilitator (mirroring the examples' no-key CI fallback and payment.rs test HTTP stub) or the existing loopback-only devnet substrate.
4. 5. ADR-0015 governance: Status is Proposed. Under the house rule ('invalid policies reject at load time'; ADRs are normative) confirm whether landing follow-up B in Rust requires moving the ADR to Accepted first, and whether follow-up A (Solidity allowlist) stays deferred until then.

## Risks

1. Signed-artifact/wire breakage: LiabilityClaimAdjudicationArtifact is a SignedExportEnvelope. Adding a REQUIRED decision_rule_ref changes canonical JSON and invalidates every existing signature/fixture/conformance vector (regen + spec/PROTOCOL update). An OPTIONAL field with skip_serializing_if=Option::is_none is signature-safe when absent - favor that for 'cheap now'.
2. validate() signature churn: changing LiabilityClaimAdjudicationArtifact::validate() to take a roster breaks all callers (store-sqlite, control-plane, kernel re-exports). Prefer a separate validate_against_roster(&self, roster) so validate() stays shape-only, but then every value-movement caller must be updated to call it or the constraint is not actually enforced on the payout chain (settlement.rs L103 calls validate(), not the roster check).
3. Fail-open payment: authorize_payment_if_needed returns None when no adapter (validation.rs L1235) and MeteredSettlementMode::MustPrepay (governance.rs L56) is not enforced in the kernel payment path. Productizing without a fail-closed 'rail mandate present -> adapter required, else deny' rule would let a governed intent that mandates prepayment execute unpaid.
4. Custody creep: any move to broadcast EIP-3009 authorizations, hold the payer signature, or run an escrow-backed x402 mode crosses the custody-neutral boundary. Keep the off-chain lanes prepare/verify/facilitator-delegated; keep operator-managed-custody flags explicit.
5. Crate-dependency cycles: pulling the roster from chio-trust-market-context/chio-commerce-order into chio-market risks a cycle (control-plane depends on all three). Pass the roster in from the caller.
6. Two-x402-surface confusion: a plan that 'wires x402' must not accidentally leave the kernel HTTP adapter and the chio-settle EIP-3009 digest lane as two unlinked notions of x402. Decide which is authoritative and how (if at all) they compose.
7. Solidity immutability: ChioBondVault has no admin/upgrade lane (ADR-0015 D1). Follow-up A cannot be retrofitted to a deployed immutable contract; it requires a new deployment, so it must stay deferred and out of the Rust 'cheap now' scope.

## Adversarial review

**Issues:**
- FALSE CLOSURE (M2, primary): The fail-closed 'MustPrepay requires adapter => DENY' gate is placed inside authorize_payment_if_needed near L1235, which is AFTER the `let Some(charge) = charge_result else { return Ok(None) }` early-return at L1232-1234. A governed MustPrepay intent with no budget charge (charge_result == None) bypasses the gate entirely and executes unpaid - the fail-open persists exactly where it matters. Worse, the authorize amount is charge.cost_charged (validation.rs L1276), tied to the budget charge, NOT metered_billing.quote.quoted_cost, so 'prepay the quoted amount' is not what actually gets authorized. The acceptance test M2(a) will almost certainly configure a grant so charge_result is Some, pass, and leave the no-charge path fail-open and untested. Verified: validate_metered_billing_context (governed_validation.rs L276-351) never reads settlement_mode, so nothing else enforces MustPrepay either.
- FIDELITY GAP vs ADR (M1): Passing the adjudicator roster as a raw operator-config &[String] mechanically satisfies 'constrain adjudicator to a roster' but drops ADR-0015 follow-up B's requirement (L260-265) that it be 'a predeclared roster or authority anchored in a registry.' An unanchored config list can be edited per-adjudication by the same operator who holds the signing key, so validate_against_roster proves nothing in an audit. The repo already has the signed anchor form (chio-trust-market-context AdjudicationJurisdictionReceipt.adjudicator_subjects, a signed artifact) - reducing to a bare Vec<String> loses the 'anchored' property the ADR asks for.
- STANDING-INVARIANT RISK (M1): validate() stays shape-only and enforcement relies on the three control-plane constructors. Verified those ARE the only non-test construction sites today, so it is currently sufficient - BUT settlement.rs L103/211/303/488 call only the shape-only validate(). Nothing fails-closed to stop a FUTURE construction/value-movement path (store-sqlite replay, a new kernel re-export, another host) from minting a payout from an off-roster adjudication. The split validate/validate_against_roster design makes the roster opt-in per call site.
- MINOR (M1 id fold): Folding decision_rule_ref into the adjudication_id hashed tuple (liability.rs L1218-1227) changes the derived id for ALL newly-constructed artifacts even when the field is None (adding `&None` to the tuple changes canonical bytes). This does NOT invalidate existing signed fixtures (they carry their id literally; skip_serializing_if keeps serialized bytes stable) but WILL change any construction-time id golden for the None case. The plan's golden only covers serialization stability, not id-derivation stability.
- MINOR (M3 soft gate): 'refuse to start when a rail mandate is permitted but no adapter resolves' is data-dependent - intents carry mandates at runtime, not in operator config - so the CLI generally cannot know at load time whether a mandate 'may' arrive. The load-time check is at best a config-consistency nicety; the real enforcement is the M2 runtime gate. As written it over-promises fail-closed behavior at load time.
- MINOR (framing): The plan and research assert 'control-plane depends on all three' (chio-market/trust-market-context/commerce-order). Verified FALSE: control-plane does NOT directly depend on chio-market (only chio-core, which re-exports it). The cycle-avoidance conclusion is unchanged and even safer, but the dependency claim should be corrected to avoid a wrong mental model when wiring the roster.
