## Goal

Two provable outcomes, both fail-closed and within the launch-acceptance non-claims discipline: (1) a single narrated one-command operator story that walks a viewer through mandate/allowance -> over-limit attempt DENIED (signed receipt) -> in-budget attempt ALLOWED via x402/AP2/ACP-Commerce (signed receipt) -> settlement green, runnable as a regression asset in the release-qualification lane; and (2) one versioned, schema-governed spend/exposure contract (chio.comptroller.surface-report.v1) that is a pure projection over the existing OperatorReport (kernel) + ExposureLedgerReport (credit) + RiskComptrollerReport (risk) types, published as JSON Schema under a new spec/schemas/chio-comptroller/v1 namespace, enforced by the schema-registry gate, and consumed by both the in-repo dashboard (generated TS, no hand-maintained drift) and the out-of-repo dashboard (schema + optional signed export). Reuse, never rebuild: the atomic budget_store ledger, ExposureLedgerReport/SignedExportEnvelope, the comptroller/telemetry-projection schema templates, load_behavioral_feed_signing_keypair, check-chio-transaction-passport.sh, and launch_acceptance.

## The real gap

TWO distinct gaps; the second is the real engineering.

GAP 1 - DEMO ASSEMBLY / FRAMING (small to medium):
- The "wall stops money" arc is proven as a VERIFY-GREEN fixture bundle plus a UI, but there is no single narrated one-command operator story that walks a viewer through: here is the mandate/allowance, here is an over-budget attempt DENIED (this signed receipt), here is an in-budget attempt ALLOWED via x402/AP2/ACP-Commerce, here is settlement green. The allow and deny receipts coexist in the positive bundle as coverage artifacts, and the over-budget denials live as SEPARATE negative fixtures the verifier rejects. What is missing is the narrative wrapper / single entrypoint + operator-facing explanation, not the cryptographic evidence.
- It is not wired into the release-qualification lane SCRIPT: scripts/qualify-release.sh does NOT call check-chio-transaction-passport.sh or launch-acceptance (grep count 0). Those gates live only in .github/workflows/ci.yml. To satisfy "runnable in the release-qualification lane as a regression asset" either add both gates to scripts/qualify-release.sh or explicitly define ci.yml as the lane.
- The LIVE variant (examples/agent-commerce-network) is not in any CI script and does not emit a Proof Room bundle that verifies green. Bridging a live sidecar run to a signed Proof Room bundle is a larger, separate effort and depends on Direction A (authoritative kernel mediation of the sidecar tool-call path).

GAP 2 - UNIFIED SPEND/EXPOSURE DATA CONTRACT (medium, genuinely missing):
- The aggregate spend/exposure read models are NOT schema-governed. OperatorReport has no `schema` field and no signed envelope. There is NO published JSON Schema for operator-report, exposure-ledger, cost-attribution, settlement-reconciliation, metered-billing, budget-utilization, or authorization-context. I confirmed spec/schemas has no chio-credit / chio-operator / chio-comptroller namespace; the only file matching "operator-report" is spec/schemas/chio-pheromone/v1/relay-operator-report.schema.json (unrelated pheromone relay).
- Contrast: the transaction/passport/risk/enterprise SIDE is fully schema-governed (spec/schemas/chio-commerce/v1/*, chio-risk/v1/comptroller-report.schema.json, chio-enterprise/v1/*), registered in spec/schemas/registry.json and enforced by chio-core-types signed_artifact_schema tests. The live spend/exposure operator side has none of this.
- The only cross-language "contract" is the hand-maintained dashboard/src/types.ts mirror: in-repo only, unenforced, drift-prone. An out-of-repo comptroller dashboard has nothing versioned to compile against.
- Missing deliverable: ONE unified, versioned spend/exposure contract (a projection/envelope over the existing OperatorReport + ExposureLedgerReport + RiskComptrollerReport types), a published JSON Schema set (e.g. spec/schemas/chio-comptroller/v1 or chio-operator/v1) registered in registry.json + MANIFEST.sha256 + signed_artifact.rs known-schemas test, optionally a SignedExportEnvelope wrapper (mirroring SignedExposureLedgerReport), and a codegen/validation gate so the external dashboard and the in-repo TS mirror derive from one source. The enterprise telemetry-projection (signed, hash-linked events + risk_comptroller_report_ref) is a proven template to reuse for the aggregate case.

## Prerequisites

1. Decide demo scope FIRST: the STATIC Proof Room bundle path (deterministic, no key, already ~90%, CI-clean) versus a LIVE end-to-end path (agent-commerce-network + real sidecar). The static path has no external dependency; the live path hard-depends on Direction A (authoritative kernel mediation / execution_nonce in chio-api-protect) to legitimately claim a live wall. Recommend static as the v1 flagship, live as a follow-on.
2. Treat the kernel/credit Rust types as the single source of truth. The unified contract MUST be a projection/envelope over the existing OperatorReport (chio-kernel/src/operator_report) + ExposureLedgerReport (chio-credit) + RiskComptrollerReport (chio-risk) types, never a parallel model. Any new schema derives from serde output of these types.
3. Follow the established schema-governance pipeline exactly: new JSON Schemas must be added under spec/schemas/<ns>/v1, registered in spec/schemas/registry.json, hashed into spec/schemas/MANIFEST.sha256, and (if signed) named in crates/core/chio-core-types/src/signed_artifact.rs with a matching known_signed_artifact_schemas test entry. This mirrors how chio-commerce/chio-risk/chio-enterprise are governed.
4. Deterministic signing keys already exist for the demo (CHIO_COMMERCE_TRUSTED_*, CHIO_TRANSACTION_TRUSTED_ROOT_KEYS, CHIO_PROOF_ROOM_TRUSTED_* in check-chio-transaction-passport.sh). 5. Confirm the target consumption model for the out-of-repo dashboard: live HTTP polling of /v1/reports/* (implies an OpenAPI-style contract) versus a periodically exported signed bundle (implies a signed-artifact schema like enterprise-export). This decision shapes the entire contract deliverable.
6. The Proof Room + launch-acceptance are fail-closed and the repo has a strict non-claims discipline (xtask/src/launch_acceptance.rs write_non_claims; PROOF_ROOM_QUICKSTART disclaims any public-availability state). Any demo framing must stay inside that discipline (no live-availability or fund-custody claims).

## Risks

1. Contract triplication drift: today there are already two representations (Rust types + hand-written dashboard/src/types.ts). Adding a JSON Schema without a generator makes three. Without a serde-derived schema + a conformance test, the schema, the Rust type, and the TS mirror will drift. Mitigate with a codegen or a round-trip validation gate.
2. Honesty boundary: the static demo proves the wall at the ARTIFACT/verifier level (pre-signed fixture receipts regenerated by fixture.rs), NOT a live kernel intercepting a real payment. This is a legitimate, strong proof, but must not be marketed as a live money-stop. Overclaiming would violate the launch-acceptance non-claims gate.
3. Live-demo dependency on Direction A: making agent-commerce-network the flagship means its sidecar tool-call path must be authoritatively kernel-mediated. That is unresolved Direction A work and would also add Python/uv + multi-port + network flakiness to CI (smoke.sh launches 4 services). The static bundle avoids all of this.
4. Fixture re-seal blast radius: the flagship bundle is hash-linked (manifest sha256 refs, 51 negative_cases, evidence-graph digests) and machine-generated. Changing the demo shape forces regeneration/re-sealing across catalog.json + launch-acceptance + release-truth fixtures; easy to leave a stale digest that fails the fail-closed gate.
5. House rules: canonical JSON (RFC 8785) is mandatory for any signed payload; unwrap_used/expect_used are denied workspace-wide; no em dashes anywhere. A new SignedExportEnvelope schema and any builder code must comply.
6. Custody-neutral constraint (v1): settlement in the demo is a verify-only x402/AP2/ACP-Commerce projection over an offline PSP (payment-lifecycle psp stripe-shaped-offline; settlement-packet status settled via verified_cache witness). The contract and demo must not imply fund-holding; keep it a projection.
7. Scope creep on "unified": the operator surface spans many endpoints (operator, exposure-ledger, cost-attribution, settlements, metered-billing, authorization-context, capital-book, credit-scorecard). Defining ONE contract risks either being too thin (just OperatorReport) or boiling the ocean. Needs an explicit MVP field set tied to the demo narrative (mandate/allowance, reserved/settled/pending/failed exposure, deny/allow counts, settlement reconciliation state).
