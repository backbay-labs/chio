## Iteration 1 - 2026-06-15

### (a) Research snapshot

- **iroh core: 1.0.0**, published to crates.io 2026-06-15 (verified via crates.io API and docs.rs/iroh). Dual MIT/Apache-2.0; "p2p quic connections dialed by public key." First stable 1.0, following rc.0/rc.1 (rc.1 ~2026-05-27). 1.0 ships **both wire-protocol and language-API stability across 1.x minors** (a v1 endpoint interoperates with any other v1 endpoint regardless of minor); many public types are `#[non_exhaustive]` for additive evolution. This is the headline reason 1.0 is now viable as a long-lived transport. MSRV raised to Rust 1.91.
- **Core scope = connectivity only:** `Endpoint` (`Endpoint::builder(preset)`/`bind(preset)`), `protocol` module (`Router` + `ProtocolHandler` for ALPN multiplexing), ALPN negotiation, relay client + `RelayMode`/`RelayUrl`, QUIC transport with multipath + NAT traversal/hole-punching, in-core `address_lookup` (discovery) traits/impls. Siblings versioned independently: iroh-base, iroh-relay, DNS discovery, iroh-metrics, iroh-tickets, iroh-util (AccessLimit), mDNS / Mainline-DHT backends.
- **Big 1.0 rename (the dominant gotcha):** `NodeId`/`NodeAddr` -> `EndpointId`/`EndpointAddr`; `node_id()`/`node_addr()` -> `id()`/`addr()`; the `discovery` module -> `address_lookup` (`Discovery` trait -> `AddressLookup`). `EndpointId` is a 32-byte ed25519 pubkey. Any NodeId/NodeAddr tutorial is pre-1.0 and will not compile.
- **Higher-level crates are still 0.x and NOT covered by the 1.0 promise:**
  - `iroh-gossip` **0.101.0** (2026-06-15, n0, MIT/Apache-2.0). Depends on `iroh = "1"` / `iroh-base = "1"`, so it targets the 1.0 core, but is itself 0.x (expect breaking minor bumps). Epidemic broadcast trees (HyParView + PlumTree); register `Gossip` as a `ProtocolHandler` on a `Router`, `subscribe`/`subscribe_and_join` a 32-byte `TopicId`, split `GossipSender`/`GossipReceiver`. **Most directly relevant crate for a federation/gossip mesh.**
  - `iroh-blobs` **0.103.0** (2026-06-15, still n0). Depends on `iroh`/`iroh-base`/`iroh-tickets` `1.0.0`. CAVEAT: README says the current 0.10x line is "not yet considered production quality" and points production users to the older **0.35**. BLAKE3 verified streaming; `BlobsProtocol` mounted on a `Router`, content-addressed by 32-byte BLAKE3 hash, shared via `BlobTicket`. Relevant only if content-addressed bulk transfer is needed (e.g. catch-up roots).
- **Discovery mechanisms (modular, partly out-of-core):** in-core `MemoryLookup` (static manual `EndpointAddr` injection), in-core `DnsAddressLookup` (n0 public instance via `::n0_dns()`), in-core Pkarr publish/resolve over a pkarr relay (HTTP); out-of-core `iroh-mdns-address-lookup` (LAN) and `iroh-mainline-address-lookup` (pkarr over BitTorrent Mainline DHT); plus fully-manual static `EndpointAddr` (id + direct addrs + optional `RelayUrl`, no discovery service). For a controlled federation, global discovery can be skipped entirely (dial via manually-constructed `EndpointAddr`) or run on a private pkarr/DNS.
- **Other findings relevant to the federation fit:** raw-public-key TLS authenticates the exact peer key on connect with no CA/PKI (auth, not authz - still need our own operator-allow-list layer); **relay self-hosting is supported** (iroh-relay ships an OSS relay server with ACME/Let's Encrypt, relays forward only encrypted traffic keyed by EndpointId); 0-RTT supported (keep payloads idempotent); first-class embedded/mobile bindings (Swift/Kotlin/Python/Node).

- **Dial-by-key ergonomics (the core question):**
  - The type is `iroh::EndpointAddr` (re-export of `iroh_base::EndpointAddr`) = `EndpointId` (ed25519 pubkey) + a set of `TransportAddr` (`Ip(SocketAddr)` | `Relay(RelayUrl)` | `Custom`). Client dial: `client_ep.connect(server_addr: impl Into<EndpointAddr>, alpn: &[u8]) -> Result<Connection, ConnectError>`.
  - **`EndpointId` alone also `impl Into<EndpointAddr>` and compiles, but resolving it requires a discovery service** - for a discovery-free local dial you MUST pass the full `EndpointAddr`. This is the concrete shape of the (kernel_id, NodeId) collapse plus reachability that ADR-0014 anticipates.
  - **Foot-gun:** `Endpoint::addr()` is synchronous and may return an `EndpointAddr` with no direct IPs right after `bind()`, stalling the dial. Correct pattern is `Endpoint::watch_addr() -> impl iroh::Watcher<Value=EndpointAddr>`, loop until `addr.ip_addrs().next().is_some()` (PoC used a 10s timeout fallback; resolved sub-second on LAN). Builders: `EndpointAddr::new(id).with_ip_addr(sock).with_relay_url(url)` / `EndpointAddr::from_parts(id, [TransportAddr])`.
- **ALPN + accept ergonomics:** `const ALPN: &[u8] = b"chio-federation/0";`. Implement `iroh::protocol::ProtocolHandler` (Debug + Clone + Send + Sync + 'static); 1.0 method is `async fn accept(&self, connection: Connection) -> Result<(), AcceptError>` (`?` auto-converts Connection/IO/quinn errors). Inside: `accept_bi().await?` then `tokio::io::copy` then `send.finish()?` then `connection.closed().await`. Mount via `Router::builder(server_ep).accept(ALPN, Echo).spawn()`; `router.endpoint()` for access back, `router.shutdown().await?` to stop (aborts on drop). Client I/O: dialer `open_bi`, acceptor `accept_bi` (directionality matters); `send.finish()?` is NOT async; `conn.close(0u32.into(), b"done")` is sync.
- **Imports that compile (1.0.0):** `use iroh::{Endpoint, EndpointAddr, Watcher, endpoint::{Connection, presets}, protocol::{AcceptError, ProtocolHandler, Router}};`. Bind: `Endpoint::bind(presets::N0).await?` (also `Minimal` / `N0DisableRelay` / `Empty`). `iroh_base` re-exports `{EndpointAddr, EndpointId, PublicKey, SecretKey, TransportAddr, RelayUrl, Signature, ...}`.
- **Friction / budget items:** the **Node\* -> Endpoint\* rename** dominates (the researcher sketch matched the shipped API almost verbatim once renamed); early-`addr()` empty-direct-addrs foot-gun (use `watch_addr`); **large dependency surface** (iroh 1.0 = 409 locked crates; quinn/rustls 0.23.40/hickory-resolver/igd-next/portmapper/reqwest/objc2-* on macOS; cold debug build ~1m55s); `cargo add iroh` pulls a big default feature set (fast-apple-datapath, metrics, portmapper, tls-ring) - a slim federation transport likely wants `default-features=false` + curated relay/tls; `Watcher::updated()` returns `Result` (Err = all Endpoint clones dropped; does NOT disconnect on mere close) so handle the Err arm or hang; macOS has no `timeout` coreutil (PoC self-terminated via internal deadline). **errors: none.**

**New gaps surfaced (carry into ADR + next iterations):**

1. **Revocation-gossip identity is NOT the same as pheromone; the mapping table treats both lanes uniformly.** Pheromone has an issuer-signed `PeerDirectory` binding `(kernel_id, public_key, endpoint)` and verifies an envelope signature against the pinned `public_key` (`directory.rs:60-73`, `http_signing.rs:78-86`). Revocation gossip has **no directory, no endpoint, no public_key in its wire types at all**: `RevocationGossipBatch`/`RevocationRootGossip` carry only `recipient_kernel_id` + an opaque `signer_id: String`, verified against an out-of-band pinned signer key the receiver already holds (`revocation_gossip.rs:45-47,64-65,125-128,206,372`; the module names `KernelTrustExchange` as the source of truth for who may participate). Under iroh, pheromone can reuse its signed directory to map kernel_id->NodeId; revocation must acquire a **brand-new** signer_id->NodeId (and signer_id->verifying-key) binding.
2. **Bilateral DSSE co-signing transport is unaddressed.** `bilateral_dsse.rs:406-428` defines a standalone `DsseEnvelope { payload_type, payload, signatures: Vec<DsseSignature{keyid,sig}> }` with in-toto DSSE-PAE semantics, **no push queue, no recipient field, no transport**. It is a request/response handshake (`DsseCoSigningRequest`, `BilateralCoSigningProtocol` in `bilateral.rs`), not fire-and-forget gossip, so it does NOT fit the "drain push-queue batches into iroh-gossip publishes" adapter shape, even though the Decision's Drop-In Seam step 2 lists a "bilateral co-sign exchange" ALPN. It is a **third "first implementation" case** and needs a separate interactive bidirectional QUIC stream.
3. **PQ / non-Ed25519 keys vs iroh's ed25519-only NodeId forces Option B (not merely recommends it).** chio-core-types supports hybrid ed25519+ML-DSA-65 (`SigningAlgorithm::Hybrid`, `HYBRID_ED25519_MLDSA65`) plus P256/P384, and `chio-federation` has a `pq` feature (`Cargo.toml:16`). `PublicKey::as_bytes()` panics for any non-Ed25519 key (`crypto.rs:546-562`), and an iroh NodeId IS a 32-byte ed25519 key. Therefore **Option A (passport key == NodeId) is impossible for any operator with a hybrid/P256/P384 passport** - it would force all federating operators onto Ed25519 passports and abandon the PQ-hybrid posture. Option B (rotatable Ed25519 transport NodeId published in the signed record, decoupled from a possibly-PQ passport) is **mandatory** for PQ/FIPS operators.
4. **Transit-hub set inherits the kernel_id->NodeId resolution problem.** `PheromoneTransitPolicy.accepted_hubs` is a `Vec<String>` of kernel_ids (`pheromone_gossip.rs:137`) and transit chains pin per-hop ladder manifests against directory `accepted_ladder_refs`. The ADR says URL/endpoint plumbing "goes away," but the transit-hub policy still addresses hubs by kernel_id, so the hub set must ALSO be re-addressed to NodeIds; the URL-bound relay profiles (`RelaySupervisorProfileDocument`, `RelayReverseProxyProfile`, `validate_endpoint` loopback/https rules) are the substrate that disappears.
5. **Transport-key rotation couples to the directory's anti-rollback machinery.** The pheromone directory enforces strict monotone versioning, `previous_version_sha256` chaining, and a `version_floor` rollback gate (`directory.rs:302-307,452-534`). Publishing a rotatable transport NodeId (Option B) inside this signed directory makes NodeId rotation a directory bundle re-issue + promotion, coupling transport-key rotation cadence to directory issuance cadence and the rollback rules it must respect. Drop-In Seam step 1 should acknowledge this.

- **built: yes. ran: yes. broadcast observed: yes.** 3-node chain join (A seed; B bootstraps from A; C from B). A broadcasts once; B receives it as A's direct neighbor, C receives it relayed through B. Stable across 4 consecutive runs, exit 0 each, ~no startup delay on loopback. Multi-hop works.
- **Real API shape (0.101.0):**
  - Construct: `Gossip::builder().spawn(endpoint.clone())` returns a `Gossip` that impls `iroh::protocol::ProtocolHandler`. Mount: `Router::builder(ep).accept(iroh_gossip::ALPN, gossip.clone()).spawn()`. ALPN constant `iroh_gossip::ALPN` (= `net::GOSSIP_ALPN` = `b"/iroh-gossip/1"`). The crate's own tests ALSO advertise it on the endpoint builder via `.alpns(vec![GOSSIP_ALPN.to_vec()])` in addition to the Router accept; doing both works.
  - Join: `gossip.subscribe_and_join(topic: TopicId, bootstrap: Vec<EndpointId>).await -> Result<GossipTopic, ApiError>`. It internally awaits the first `NeighborUp`, so it returns only once there is >=1 live neighbor. Non-blocking variant `subscribe(topic, bootstrap)` returns immediately; call `GossipTopic::joined().await` yourself. `subscribe_with_opts(topic, JoinOptions::with_bootstrap(ids))` sets `subscription_capacity`.
  - Split: `GossipTopic::split() -> (GossipSender, GossipReceiver)`. `GossipSender` is `Clone`. `GossipTopic` is itself a `Stream` and has its own `broadcast`, so splitting is optional.
  - Broadcast: `GossipSender::broadcast(Bytes).await -> Result<(), ApiError>`; also `broadcast_neighbors(Bytes)` (direct neighbors only) and `join_peers(Vec<EndpointId>)`. `bytes` is NOT re-exported by the public API; `vec.into()` / `payload.to_vec().into()` infers the `Bytes` the signature wants (no direct `bytes` dep needed unless you want to name the type).
  - Receive: `GossipReceiver` impls `Stream<Item = Result<Event, ApiError>>`. Drive with `n0_future::StreamExt` (`recv.next().await`); n0-future re-exports futures-lite's StreamExt, so no separate `futures` dep. `Event` variants: `NeighborUp(EndpointId)`, `NeighborDown(EndpointId)`, `Received(Message)`, `Lagged`. `Message { content: Bytes, scope: DeliveryScope, delivered_from: EndpointId }`.
  - **Identity gotcha (load-bearing for the batch verifier):** `Message::delivered_from` is the forwarding NEIGHBOR, NOT the original author. Confirmed empirically: node C's received message reported `delivered_from = B` (the relay hop), even though A authored it. Gossip authenticates each link's transport (an iroh connection keyed by EndpointId) but does NOT authorize message CONTENT; any admitted topic member can broadcast.
  - Topic: `TopicId` is a 32-byte id (`TopicId::from_bytes([u8;32])` const fn, or `[u8;32].into()`; `as_bytes() -> &[u8;32]`); often derived as `blake3::hash(seed).into()`.
  - Bootstrap-by-EndpointId requires address resolution. With `presets::N0` that is DNS/pkarr (network). For an offline mesh, bind with `presets::Minimal` + `RelayMode::Disabled` and register a shared `iroh::address_lookup::memory::MemoryLookup` on every endpoint (`endpoint.address_lookup()?.add(book)`), seeded with each peer's full `EndpointAddr` via `book.add_endpoint_info(addr)`. `MemoryLookup` clones share one Arc-backed map, so seeding once makes every peer resolvable everywhere. This is exactly how iroh-gossip's own `gossip_net_smoke` test wires a local mesh. **The POC ran with `RelayMode::Disabled` (loopback only), so relays were NOT exercised at all.**

### (b) Adapter sketch - Option B type-checks against iroh 1.0

- **built: yes** (`cargo build --bins`, "Finished"). The core Option-B claim is genuinely TYPE-CHECKED, not hand-waved.
- iroh 1.0 makes Option B's central fact a type-level guarantee: `iroh::EndpointId` is literally `pub type EndpointId = PublicKey` (iroh-base-1.0.0/src/key.rs:70) and `PublicKey(CompressedEdwardsY)` is ed25519. So a P256/hybrid/PQC passport simply cannot be an `EndpointId` (Option A is structurally impossible there) - exactly the motivation for a separate transport key.
- Transport key uses iroh's real primitives: `SecretKey::generate()` (no-arg, internal `rand::random()`), `secret.public() -> PublicKey`, `PublicKey` IS the `EndpointId`. Rotation = fresh `SecretKey` + re-issue directory entry; old id -> `UnknownEndpoint` after rotation (asserted).
- Passport modeled as `enum Passport { Ed25519 | P256 | Hybrid }` + opaque `kernel_id: String`; `could_be_endpoint_id()` is true only for Ed25519. Asserts prove P256/Hybrid passports still get a valid 32-byte ed25519 EndpointId via their separate transport key.
- Sign/verify uses real `SecretKey::sign(&msg)` / `PublicKey::verify(&msg,&sig)` (key.rs:111-323). `authorize_connection(presented: EndpointId, directory) -> Result<&Entry, DenyReason>` is fail-closed: denies unless an entry binds `presented` AND `allowed == true` AND the PoP signature verifies. Three deny reasons (UnknownEndpoint / NotAllowed / BadSignature), all exercised; a tamper test flips `allowed` false->true without re-signing and is rejected as BadSignature.
- **Correctly carried forward:** keeps TRANSPORT AUTH (does the QUIC peer hold the private key for EndpointId N?) separate from ARTIFACT TRUST (passport-algorithm tag recorded but plays no role in `authorize_connection`). That is the ADR-0014 seam: iroh authenticates the pipe, Chio authorizes above it. EndpointId/PublicKey are `Copy`, 32 bytes, `Eq`+`Hash`, round-trip via `from_bytes`/`as_bytes`, `fmt_short()` for logging - convenient as directory map keys.

### (c) Research

- **Relay self-hosting: CONFIRMED you can run a fully private relay set and avoid n0 entirely.** Use `iroh-relay` v1.0.0 (lib `server` module behind the `server` feature + a CLI binary). Needs a public IP + DNS name (relays addressed by HTTPS `RelayUrl`); default 443 HTTPS, separate QUIC-address-discovery (QAD) server (observed default 7824), `--dev` serves HTTP on 3340; relay/metrics/QAD roles have independent enable flags. TLS via `tokio-rustls-acme` (ACME/Let's Encrypt) or `rcgen` self-signed or reloadable manual certs (`cert_mode = "Manual"`). Point clients with `RelayMode::Custom(RelayMap)` / `RelayMode::custom([RelayUrl...])` using ONLY your own URLs; all endpoints in a federation must share the same relay map. **Relay is content-blind:** "all connections in iroh are end-to-end encrypted"; relay is "just another UDP socket," stores nothing, sees only EndpointId<->EndpointId + byte counts and only until a direct path forms. Self-hosting is about availability + metadata-minimization, NOT trust. CAVEAT: full n0 independence ALSO requires handling DISCOVERY - `RelayMode::Custom` avoids n0 relays but n0's default DNS discovery still touches n0; self-host/pin discovery (own pkarr/DNS or static `EndpointAddr`).
- **Accept-time auth hook: YES, first-class and decisive.** iroh 1.0 ships `EndpointHooks` (module `iroh::endpoint`) with two async methods returning an Outcome; if ANY hook returns Reject the connection attempt is rejected; hooks run in registration order. `before_connect(&self, remote_addr: &EndpointAddr, alpn) -> BeforeConnectOutcome` fires for OUTGOING dials before any packet (egress allowlist). `after_handshake(&self, conn: &Connection) -> AfterHandshakeOutcome` fires for BOTH directions AFTER the TLS handshake, receives the live `Connection`, exposes the CRYPTOGRAPHICALLY VERIFIED peer id via `conn.remote_id() -> EndpointId` plus `conn.side()` (`Side::Server` = inbound). `Reject { error_code: 403u32.into(), reason: b"...".to_vec() }` returns a QUIC app close code + reason. This fires BEFORE `Endpoint::accept()` yields and BEFORE any `ProtocolHandler::accept()` runs, so unauthorized peers never reach Chio's protocol logic. Register: `Endpoint::builder(presets::N0).hooks(auth_hook).bind().await?`. Reference: iroh/examples/auth-hook.rs. CAVEAT: a rejected peer does complete a (cheap) TLS handshake before being cut; pure pre-handshake gating only has `before_connect` (outgoing) + ALPN filtering.
- **iroh-gossip production-readiness:** 0.101.0 is NOT a 1.0 crate (stayed 0.x while core went stable); treat as usable-but-pre-1.0, expect breaking minor bumps. README makes NO production-readiness claim and states no formal delivery/partition guarantees. Design: per-topic epidemic broadcast trees; membership = HyParView (active view default 5 bidirectional peers + passive 30, periodic Shuffle, self-healing under churn but each node only directly gossips with ~5 neighbors); broadcast = PlumTree (EAGER full pushes + LAZY IHAVE hashes pulled on timeout). Anti-entropy: the IHAVE/lazy-pull path is the ONLY repair mechanism - strong auto-recovery on node failure but NO guaranteed eventual total delivery, NO persistent log, NO state reconciliation across a healed partition. A node offline/partitioned past timer windows can permanently miss messages. Use gossip as a fast dissemination/notification layer, NOT source of truth; layer your own anti-entropy (signed digest/snapshot exchange, or iroh-docs/iroh-blobs for authoritative state). Message size: `DEFAULT_MAX_MESSAGE_SIZE = 4096` bytes (floor `MIN_MAX_MESSAGE_SIZE = 512`); chunk large data or reference by hash and fetch via iroh-blobs.
- **0-RTT:** outbound only via `Connecting::into_0rtt(self) -> Result<OutgoingZeroRttConnection, Connecting>` (returns the Connecting unchanged if no cached TLS session). Docs verbatim: 0-RTT data "is vulnerable to replay attacks, and should therefore never invoke non-idempotent operations"; no forward secrecy. For Chio: do NOT put admission decisions, capability grants, ledger/spend ops, nonce-consuming handshakes, or vote/membership-change messages into 0-RTT early data - a replay could double-apply. Keep the control/trust plane on 1-RTT (the safe default); the admission gate is unaffected because `after_handshake` fires on handshake completion regardless. If 0-RTT is used for latency, restrict to idempotent reads + app-level replay protection (signed payloads + monotonic nonces / dedup window).
- **Other 1.0 notes:** `iroh-relay` 1.0.0 stable but `iroh-gossip` still 0.101.0 (stability is SPLIT - pin gossip carefully). DEPRECATION CLOCK: n0's free public relays end 2026-12-31, so a durable federation should self-host (or pay for n0 Iroh Services). QUIC multipath in 1.0 (relay + direct path coexist and hot-swap). Official Python/Node/Swift/Kotlin bindings are first-class.

### (d) Review verdicts

**Adapter faithfulness: directionally faithful, but materially MIS-MODELS the directory's authorization shape and trust anchor.** Treat it as a correct proof that "Option B type-checks against iroh 1.0," NOT as a faithful sketch of the real `PeerDirectory` contract. Specific gaps:

- **Gap 1 (authorization oversimplified to a boolean):** the real `PeerDirectoryEntry` has NO `allowed` flag. Authorization is presence in the BTreeMap keyed by kernel_id (directory.rs:228-235, plus a `PeerRemoved` tombstone set) AND `relay_role` (Origin/Hub/Receiver) gating direction AND `treaty_subscriptions: Vec<String>` membership AND `allowed_subject_class_namespaces` AND per-peer rate caps (max_batch_frames/max_catchup_frames/max_catchup_bytes). Real enforcement = `enforce_peer_batch_directory_scope` (service.rs:420-447): role AND treaty-subscription AND frame-count cap. The real adapter must return the entry and let the caller apply role/treaty/namespace/rate checks; a single allow bit is not the directory's authorization role.
- **Gap 2 (WRONG signer / trust anchor):** the sketch signs each Entry with the TRANSPORT key itself as proof-of-possession (adapter_sketch.rs:112-114,159) and verifies that self-signature. The real directory is NOT self-signed by the subject key: a `PeerDirectoryBundleDocument` is signed by a separate ISSUER key, verified against a pinned `TrustedPeerDirectoryIssuer{issuer,key_id,public_key}` allow-list (directory.rs:107-112,322-338). The authorization assertion "kernel K is bound to key X and admitted" is an ISSUER attestation, not a self-claim. PoP of the transport key is a useful ADDITIONAL property, but the sketch substitutes PoP FOR issuer-signing rather than layering it under it - as modeled, anyone holding a transport secret can mint an authorizing entry for any kernel_id (self-asserted directory).
- **Gap 3 (binding identifies the wrong subject + drops the cross-link):** the real directory binds kernel_id -> PASSPORT public_key (directory.rs:64), and live wire auth verifies the request envelope against THAT pinned passport key (http_signing.rs:78-86, `peer.public_key.verify_canonical(...)`). So today's shipped HTTP transport is effectively Option A (passport key == transport-auth key), which only works because envelope-signing is algorithm-agnostic (can verify a P256/hybrid passport that iroh's ed25519 EndpointId cannot). The sketch binds kernel_id -> TRANSPORT EndpointId and records passport only as an opaque string tag (no passport key bytes, no passport signature). That is the correct Option-B SHAPE for iroh, but it silently drops the signed cross-link between passport identity and transport key. Rotation (adapter_sketch.rs:370-388) generates a new ed25519 key and re-lists it with NO passport-side authorization of the new key. The real adapter needs the issuer-signed entry (or a passport-signed sub-attestation) carrying BOTH the passport key material AND the transport EndpointId so the binding is anchored in the long-term identity.
- **Gap 4 (no validity window / versioning / rollback):** the sketch's directory is a bare `&[Entry]` with no issued/expires window, no version, no rollback gate. The real model enforces a validity window (directory.rs:175-179,308-314), `min_version` floor, `previous_version_sha256` chaining, and `version_floor` monotonicity on rotation (directory.rs:302-307,473-495,516). The sketch's "rotation" (new one-entry Vec) sidesteps every rollback protection.
- **Gap 5 (canonicalization mismatch):** the sketch hand-rolls a bespoke `kernel_id || 0x00 || endpoint_id(32) || allowed(1)` layout (adapter_sketch.rs:121-128). The real system signs canonical-JSON bodies via `sign_canonical`/`verify_canonical` and pins them with `canonical_sha256` (directory.rs:266,277-280,332-335). A real adapter must bind the transport key inside the same canonical-JSON, issuer-signed, sha256-pinned envelope, not a one-off concatenation.
- **Scope note (over-claims by omission):** `authorize_connection` models accept-time gating keyed by EndpointId (a faithful model of the iroh accept seam), but it returns the bound kernel_id and never feeds it into the batch-verifier seam. The federation check ADR-0014 names as "the only thing the new transport must supply" is binding the authenticated sender to `PheromoneGossipBatchVerificationContext.authenticated_sender_kernel_id`, then checked against EVERY frame's `gossiping_peer_kernel_id` and (for direct frames) `origin_kernel_id` (pheromone_gossip.rs:236-249). So the sketch demonstrates EndpointId -> kernel_id but NOT kernel_id -> per-frame sender equality.

**ADR-0014 re-audit (claims re-checked against the live tree):**

- Rotation respects monotone versioning (Decision + Drop-In Seam step 1): **imprecise.** The directory.rs:302-307,473-495,516 mechanics are correct, but ADR-0014 never states WHO signs the binding that authorizes a rotated transport key. The real binding is an ISSUER attestation (`TrustedPeerDirectoryIssuer`, directory.rs:322-338), NOT subject-self-signed. The ADR says the transport EndpointId is "published inside the operator's signed federation record" but is silent on issuer-signed vs operator-self-signed, and on whether the passport must separately endorse the transport key.
- "iroh dials the key; the directory says whether that key is allowed" / directory keeps doing authorization (kernels admitted, relay roles, treaty subscriptions, namespace allow-lists, rate limits): **confirmed** and now concretely grounded (directory.rs:62-73; service.rs:420-447). Authorization is multi-dimensional, NOT a single allow bit (flagging because the sketch reduces it to one bool; the ADR itself is right).
- "the authenticated QUIC peer (the dialed EndpointId) would establish authenticated_sender_kernel_id ... That is the only thing the new transport must supply" (Drop-In Seam): **imprecise.** TODAY's authenticated sender is the PASSPORT key verifying a JSON envelope (http_signing.rs:78-86), which works for P256/P384/hybrid. Under iroh the authenticated peer is an ed25519 EndpointId, so for non-ed25519 operators the transport authenticates only the TRANSPORT key; mapping back to `authenticated_sender_kernel_id` REQUIRES the EndpointId->kernel_id binding to be trustworthy and current. iroh supplies an authenticated EndpointId, NOT the authenticated sender directly; the "only thing" framing hides a second required thing - binding resolution at accept time.
- Mapping table: pheromone + revocation-root + cross-operator trust gossip -> iroh-gossip topic broadcast: **imprecise.** Gossip compiles/runs on 1.0 (good), but the directed per-recipient batch contract (`PheromoneGossipBatch.recipient_kernel_id` + `flush_batches_at` keyed on (recipient,treaty); pheromone_gossip.rs:88-93,471-507) does NOT map cleanly to topic broadcast: gossip Events carry no `recipient_kernel_id` and no per-hop authenticated origin (`delivered_from` is the relay neighbor, not the author). Directed per-recipient batches map more naturally to direct per-peer QUIC streams (the ADR already hedges "or direct per-peer QUIC streams"); reserve gossip for genuine fan-out signals, and note gossip multi-hop BREAKS the EndpointId->authenticated_sender_kernel_id equality the batch verifier relies on.

**New gaps surfaced (carry into ADR + next iterations):**

1. **WHEN the admission check runs relative to iroh accept is unspecified.** iroh authenticates the EndpointId during the QUIC/TLS handshake, so the adapter CAN reject an unbound/unknown/removed EndpointId at accept time (before any stream bytes), strictly more fail-closed than verifying at batch-parse time. The ADR's "iroh sits underneath, authorizes nothing" framing leaves open whether the EndpointId->kernel_id + admitted-peer check gates the connection at accept (cheap DoS rejection, mirrors `authorize_connection` + `EndpointHooks::after_handshake`) or only later when the batch verifier runs. Recommend: fast accept-time gate (is this EndpointId bound to an admitted, non-removed kernel_id in the current directory?) AND keep the full per-frame check above it - defense in depth, not either/or.
2. **Gossip TOPIC membership vs TREATY scoping is unspecified.** The pheromone contract scopes by treaty_id at batch + frame level (`BatchTreatyMismatch`; pheromone_gossip.rs:230-235) and per-peer `treaty_subscriptions`. iroh-gossip joins are per-`TopicId`. The ADR never says whether one topic == one treaty, one topic == one federation with in-payload treaty filtering, or topic-per-(treaty,recipient). If a topic is shared across treaties, an operator subscribed to treaty A can SEE treaty-B traffic on the wire (gossip is broadcast), violating the per-treaty subscription model even though the verifier later rejects it. Commit to a topic<->treaty derivation and note the confidentiality implication of broadcast gossip vs directed streams.
3. **Cross-algorithm BINDING DIRECTION for Option B is under-specified (most important security property surfaced).** The ADR says the transport EndpointId is published in the operator's signed record, but NOT that the binding must be PASSPORT-SIGNED (the long-term, possibly-PQ key endorsing the ephemeral ed25519 transport key). Without an explicit passport-over-transport signature, an issuer-only or PoP-only binding (as the sketch models) lets the transport key float free of the long-term identity - undermining the whole point of separating them.
4. **Transport-key removal/revocation latency is unaddressed.** The directory has a `PeerRemoved` tombstone (directory.rs:229-231,605-633) and `version_floor`, but the ADR's rotation discussion only covers re-issue/promotion, not how a COMPROMISED transport EndpointId is rejected at accept time before the next directory bundle propagates. A leaked ed25519 transport secret is dialable until the directory re-issues and every receiver promotes the new version; recommend short transport-key validity / fast re-issue, distinct from the long-term passport. Blast radius is bounded by directory propagation latency.
5. **Relay self-hosting is UNVALIDATED by the POCs.** Research CONFIRMS iroh-relay is self-hostable (lib + CLI, ACME/manual certs), but iteration-2 gossip.rs ran with `RelayMode::Disabled` (loopback only), so the self-hosted-relay path is still entirely unexercised. Mark relay self-hosting as UNVALIDATED rather than implying it was checked, and note an iroh relay is content-blind (sees EndpointId + encrypted bytes only) - relay self-hosting is about availability/metadata-minimization, not trust, so Open Q4 budgeting should be scoped accordingly.

### (c) Design decisions - topic<->treaty derivation, per-lane transport table, bilateral stream

- **Topic<->treaty derivation: ONE-TOPIC-PER-TREATY, deterministic, no coordination round-trip.** `TopicId = blake3("chio-pheromone-gossip/v1\x00" || treaty_id_bytes)` (32-byte BLAKE3 used verbatim as the iroh-gossip `TopicId`). Distinct domain-separation label per gossip surface (e.g. `chio-revocation-root-gossip/v1`, `chio-trust-fanout/v1\x00 || clearing_scope_id`) so lanes never collide on the same id; label is versioned `/v1`. `treaty_id_bytes` is canonical UTF-8 of the existing `String treaty_id` (no new identifier type); blake3 is already a workspace primitive.
- **Decisive confidentiality reason per-treaty is MANDATORY:** iroh-gossip is broadcast WITHIN a topic; a topic is one swarm (HyParView/PlumTree) where every member sees every other member's wire traffic (`Event::Received`, plus `NeighborUp`/`NeighborDown`). The topic membership set IS the confidentiality boundary. Binding `TopicId` one-to-one to a treaty makes that boundary exactly the treaty's subscription set; cross-treaty leakage is structurally impossible (different swarm, different `TopicId`). A deterministic `TopicId` is NOT a secret and grants no access by itself - membership must be gated to the treaty's admitted, non-revoked participants by the accept-time `EndpointId` admission hook plus the issuer-signed directory. REJECTED: one-federation-topic-with-in-payload-filtering (in-payload filtering is a receive-side courtesy, not access control - puts every operator in one swarm seeing every treaty's frames); topic-per-(treaty,recipient) (degenerates a swarm to ~2 endpoints - if traffic is directed, use a direct QUIC stream instead).
- **Per-lane transport table:**

- **Bilateral DSSE stream sketch:** map the co-signing RPC onto ONE iroh BIDIRECTIONAL QUIC stream on a dedicated ALPN `b"chio/federation/bilateral-dsse-cosign/1"`. Org B dials Org A's EndpointId (resolved from `kernel_id` via the issuer-signed directory); the QUIC/TLS handshake authenticates both EndpointIds; Org A's `after_handshake` rejects if Org B's EndpointId is not bound to an admitted, non-revoked, in-rotation-window kernel_id BEFORE any `ProtocolHandler::accept` (DoS rejection / defense in depth, not a replacement for signature checks). Per exchange: Org B `open_bi()`, writes one length-delimited canonical `DsseCoSigningRequest { schema, org_a_kernel_id, org_b_kernel_id, pae_bytes, org_b_signature }`, half-closes send. On success Org A signs the SAME `pae_bytes` and writes `DsseCoSigningResponse { schema, org_a_signature }` on the same stream. The bidi stream gives request-on-send / response-on-recv correlation with no app-level request IDs; an iroh-stream impl of this trait replaces the `InProcessCoSigner`.
