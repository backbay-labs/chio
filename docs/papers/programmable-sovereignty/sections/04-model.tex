\section{Bounded Predicate Model}
\label{sec:model}

The Lean development specifies the small predicate library used for
differential testing. Its input is a receipt view that has already been built
from validated artifacts:
\[
\begin{aligned}
r = (&\mathit{id},\mathit{hash},\mathit{action},
      \mathit{participants},\\
     &\mathit{modeRank},\mathit{liveContinuations},
      \mathit{decision},\\
     &\mathit{failureCode},\mathit{evidenceDigests}).
\end{aligned}
\]
The model starts at this data boundary. Signature verification, canonical
serialization, clocks, durable storage, and construction of \(r\) are
implementation obligations described in Section~\ref{sec:implementation}.

\subsection{Predicate Semantics}

The predicate syntax is
\[
 p ::= \top \mid \bot \mid \mathsf{atom}(a)
       \mid p \land p \mid p \lor p \mid \neg p.
\]
The nine atom forms test receipt identity, participant membership, action
class, minimum ladder rank, receipt hash, live continuation membership,
decision, failure code, or an evidence-class and digest pair. The recursive
function \(\mathsf{evaluate}(p,r)\) returns a Boolean for every predicate and
receipt view.

A constitution is a finite list of predicates:
\[
  \mathsf{admits}(K,r)
    = \bigwedge_{p\in K}\mathsf{evaluate}(p,r).
\]
The language covers the receipt checks exercised by the reference and runtime
evaluators while remaining small enough to execute independently in Lean and
Rust.

\subsection{Finite-Domain Refinement}

For a candidate constitution \(K'\), a current constitution \(K\), and a
supplied list of receipt views \(D\), the checker computes
\[
 \mathsf{refinesOn}(K',K,D)
   = \bigwedge_{r\in D}
     \left(\mathsf{admits}(K',r)
       \Rightarrow \mathsf{admits}(K,r)\right).
\]
The direction is important: on \(D\), the candidate may reject more receipts,
but it may not admit a receipt rejected by the current constitution.

The theorem \thm{finite_refinement_exact} states
\[
\begin{aligned}
&\mathsf{refinesOn}(K',K,D)=\mathsf{true}\\
&\quad\Longleftrightarrow
  \forall r\in D.\;
  \mathsf{admits}(K',r)=\mathsf{true}\\
&\hspace{35mm}\Rightarrow
  \mathsf{admits}(K,r)=\mathsf{true}.
\end{aligned}
\]
Its forward direction,
\thm{finite_refinement_sound}, is the condition a caller can rely on after a
successful check. Both theorems are checked by Lean~4 without project-specific
axioms.

This guarantee is limited to \(D\). An empty list passes vacuously, and a list
that omits a relevant receipt says nothing about that receipt. The model proves
the checker correct for its input; it does not prove that a caller supplied a
complete deployment domain.

\subsection{Relation to Rust}

The Rust reference interpreter in \codepath{formal/diff-tests} was written
separately from \codepath{chio-runtime-core}. Both implement the receipt fields,
atom forms, Boolean syntax, constitution admission, and finite-domain check
shown above. Tests enumerate every atom and generate 1,024 cases for each of
compound predicate evaluation, constitution admission, and finite-domain
refinement.

Those tests compare the two Rust implementations. Lean checks the mathematical
definition and the refinement theorem, but the Rust evaluator is neither
generated from Lean nor connected to it by a refinement proof. Rust also
rejects predicates that exceed its size, depth, or node limits before applying
these semantics; those limits are not modeled in Lean. The receiver admission
hook performs many checks outside this bounded library. The
paper evaluates those checks through focused runtime tests and the
dispatch-capable negative path rather than treating the Lean model as a proof
of the whole receiver.
