\section{Evaluation}
\label{sec:evaluation}

We ask four questions. RQ1 tests whether the implementation rejects the
attacks in the threat model before dispatch. RQ2 compares the independent Rust
reference interpreter with the runtime bounded evaluator. RQ3 measures the
pre-dispatch denial path, the complete local buyer workflow, and their main
components. RQ4 reports replay coverage and package size.

\subsection{Method}

Experiments ran on Linux/aarch64 with eight Arm Neoverse-N1 cores and
49.2~GB RAM, using rustc~1.93.0 and Cargo~1.93.0. Bilateral measurements use
the release profile. The end-to-end workflow uses persistent SQLite stores on
one host and includes process startup, package generation, CLI execution,
schema validation, and semantic review.

\codepath{run-bilateral-admission.sh} performs two warmups,
\PSPathSampleCount{} samples for each complete workflow, and
\PSCriterionSampleCount{} samples for each component. It retains raw CSV,
machine and toolchain metadata, a JSON summary, and generated \TeX{} macros.
\codepath{run-replay-corpus.sh} reports the generic capability corpus and the
bilateral negative matrix separately.

\subsection{RQ1: Do Attacks Deny Before Dispatch?}

The corpus contains \PSThreatCaseCount{} cases,
\codepath{PS-TH-01} through \codepath{PS-TH-20}. Each entry names the test
target, expected failure code, enforcement phase, and expected dispatch state.
The runner rejects duplicate identifiers, empty selections, unexpected codes,
and any case that expects dispatch.

All \PSThreatCaseCount{} cases returned the expected denial code in both matrix
runs. These focused cases stop at the validator or admission hook and do not
install a tool server. The dispatch-capable denial benchmark supplies the
separate non-invocation observation: its counter remained zero. Running the
complete release matrix took \PSNegativeMatrixSeconds~s.

One assumption cannot be tested by this corpus. If one actor controls both
private keys that the receiver authorized for the two participants, the
cryptographic profile still passes. We record this as \codepath{PS-A-01}
rather than counting it as an attack rejected by the implementation.

\subsection{RQ2: Do the Rust Evaluators Agree?}

The test suite covers every atomic predicate form, then runs 1,024 generated
cases for each of three properties: compound predicate evaluation,
constitution admission, and finite-domain refinement. For every tested input,
the independent Rust interpreter and \codepath{chio-runtime-core} returned the
same result. The generator keeps its predicates within the runtime's size,
depth, and node limits.

The Lean model in Section~\ref{sec:model} defines the same data and Boolean
operations and proves the finite-domain theorem. The differential suite,
however, compares Rust with Rust. It is useful for finding implementation
drift, not a proof that Rust is equivalent to Lean or that the surrounding
admission hook is verified.

The most direct measure of the paper's enforcement path is the pre-dispatch
denial: \PSPredispatchDenyPFiftyMs~ms p50 and
\PSPredispatchDenyPNinetyNineMs~ms p99. The timed body traverses the kernel's
capability and federation checks, resolves the stored treaty, ladder,
continuation, lineage, invocation, and bilateral statement, verifies a signed
policy denial, and writes the signed denial receipt to SQLite. The tool counter
remained zero.

The complete local buyer workflow measured
\PSBuyerWorkflowPFiftySec~s p50 and
\PSBuyerWorkflowPNinetyNineSec~s p99. This number is not receiver-hook latency.
It includes three-vendor process orchestration, package generation, persistent
storage, buyer CLI startup, schema validation, and semantic review. Producer
mode measured \PSProducerPFiftyMs~ms p50. The
\PSBuyerPathMedianDifferenceMs~ms difference between the workflow medians is
also not a clean ablation because full mode performs additional CLI and schema
work. The isolated offline package verifier measured
\PSBuyerVerifyPFiftyMs~ms p50.

Among the components, receipt signing measured
\PSReceiptSignPFiftyUs~\(\mu\)s p50, strict bilateral DSSE verification
measured \PSBilateralVerifyPFiftyUs~\(\mu\)s, and a persistent SQLite append
measured \PSReceiptAppendPFiftyUs~\(\mu\)s. These measurements isolate real
library functions, but their sum is not the complete workflow because it omits
orchestration and validation outside the timed component bodies.

\subsection{RQ4: Replay and Package Size}

The buyer package was \PSProofPackageBytes{} bytes
(\PSProofPackageKiB~KiB). The replay script validated
\PSGenericReplayCases{} generic capability fixtures in
\PSGenericReplaySeconds~s and, separately,
\PSBilateralReplayCases{} bilateral negative cases in
\PSBilateralReplaySeconds~s. The generic corpus checks stable capability
verdicts. The bilateral corpus checks the failures in
Table~\ref{tab:threat-matrix}; its coverage is not inflated by the larger
generic count.

\subsection{Measurement Limits}

The deterministic single-host setup removes network variance and makes package
comparison reproducible. It does not estimate wide-area latency, concurrent
load, or partial-failure behavior. The sample counts characterize this machine
and are not service-level objectives. The supplementary package records the
source, scripts, raw samples, and environment needed to reproduce the
experiment.
