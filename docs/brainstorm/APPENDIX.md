# Appendix: Chio Autonomous-Commerce Brainstorm (raw agent output)

Produced by a 33-agent workflow: 5 grounding, 18 ideation lenses (100 ideas), 6 red-team critics, 3 candidate framings, 1 synthesis.


## Grounding digest (what the code and market actually show)

### ground:chio-economy
The Chio repo already contains a deep, mostly-real autonomous-commerce stack, far beyond the "in-flight modules" framing in the premise. The agent-facing economic primitives exist and are tested: a capability marketplace where an agent submits a signed bid and a provider mints a scoped, time-bounded, cost-capped CapabilityToken against a verified funds reservation (chio-open-market/bidding.rs); monetary budget enforcement both flat (chio-metering/budget.rs) and hierarchical org->dept->team->agent (chio-metering/budget_hierarchy.rs); per-receipt cost metering wired into the kernel as a credit-evaluator hook that mints signed IOUs post-dispatch (chio-credit/hook.rs); and an attested commerce-order passport that verifies AP2 checkout/payment mandates and ACP delegated-payment tokens plus a full PSP payment lifecycle (chio-commerce-order/*). Real on-chain settlement exists behind a web3 feature flag: chio-settle executes EVM escrow/bond-vault lock/release/impair/refund, EIP-3009 transfer-with-authorization, x402 payment requirements, Circle nanopayments, ERC-4337 paymaster, CCIP cross-chain and Solana parity, driven by a multi-party signed capital-execution instruction (operator treasury + custodian authority chain) in chio-credit/capital_and_execution.rs. The critical design boundary: the capital/credit layer is "simulation-first / custody-neutral" by default (automatic_capital_execution_supported=false, external_execution_authoritative=false); it produces signed instructions and lets the settlement rail (crypto) or a manual fiat rail actually move funds. There is a real liability/insurance market (quote/bind/claim/adjudication/payout, chio-market) and an autonomous pricing+capital-optimization layer that runs in Shadow/Advisory/Active modes (chio-autonomy). The biggest gaps for an Orca fusion are surface-level, not economic: there is no long-running kernel HTTP/JSON-RPC server (integration is the in-process kernel or the `chio` CLI emitting signed JSON), no fiat custody execution, and no UI beyond a small bundled React dashboard in chio-cli.
Capabilities today: Capability marketplace bid/ask/accept: chio-open-market/src/bidding.rs implements bid() -> SignedAskResponse that mints a scoped CapabilityToken (server_id/tool_name, max_invocations, max_cost_per_invocation, max_total_cost) bound to the agent subject, and accept() which requires a signature-verified VerifiedReservationReceipt covering the token's total liability. Fail-closed against revoked/stale/expired listings, scope widening, currency mismatch, under-priced bids.; Monetary budget enforcement: chio-metering/src/budget.rs BudgetEnforcer/BudgetPolicy enforces max_total + per-session/per-agent/per-tool limits with saturating arithmetic and typed BudgetViolation. chio-metering/src/budget_hierarchy.rs BudgetTree enforces org->department->team->agent caps per BudgetWindow (Daily/etc) against a caller-supplied SpendSnapshot, fail-closed BudgetDecision.; Per-receipt cost metering + IOU minting: chio-metering/src/cost.rs (CostMetadata, CostDimension) and chio-credit/src/hook.rs CreditEvaluatorHook, which the kernel invokes on each finalized signed receipt to mint a signed IouEnvelope (chio.credit.iou-envelope.v1) binding amount_units/currency to receipt_id + content/policy hashes. Zero-price receipts skip minting.; Capital book + capital-execution instructions: chio-credit/src/credit/capital_and_execution.rs models a full ledger (Commit/Hold/Draw/Disburse/Release/Repay/Impair), CapitalExecutionInstructionArtifact with a multi-party signed authority chain (OperatorTreasury + Custodian), execution rails (Manual/Api/Ach/Wire/Ledger/Sandbox/Web3), execution windows, and reconciliation (observed vs intended amount). Plus CapitalAllocationDecisionArtifact (Allocate/Queue/ManualReview/Deny) and a CreditBondedExecutionControlPolicy with a kill switch.; Credit underwriting/scoring: chio-credit risk_reports + chio-credit/lib.rs define ExposureLedger, CreditScorecard (bands Prime..Restricted), CreditFacility (grant/manual-review/deny with terms: credit_limit, utilization_ceiling_bps, reserve_ratio_bps, concentration_cap_bps), CreditBond (lock/hold/release/impair), and loss-lifecycle/backtest/provider-risk packages.; Attested commerce-order passport: chio-commerce-order verifies a CommerceOrderVerificationBundle: SHA-256-pinned event log replayed through a fixed state machine (intent_recorded -> provider_admitted -> quote_bound -> mandate_bound -> budget_reserved -> payment_verified -> fulfillment_attested -> settlement_dispatched -> settlement_reconciled -> completed), a CommercePaymentLifecycle (PSP, payment_intent, manual capture before expiry, fraud/dispute/refund/chargeback/transfer-reversal states), and a CommerceMandateLedger carrying AP2 checkout+payment mandate hashes and an ACP delegated-payment-token hash with occurrence/single-use limits.; Real on-chain settlement (feature = web3): chio-settle/src/evm/* does live eth_sendTransaction/eth_call/eth_getTransactionReceipt, escrow create/merkle-release/dual-sign-release/refund, bond-vault lock/release/impair/expiry, ERC20 approve, reading EscrowSnapshot/BondSnapshot from contract state, gas estimation, RPC egress contract (no redirects, size caps). chio-settle/src/payments.rs adds x402 PaymentRequirements, EIP-3009 transfer-with-authorization digests, Circle nanopayments, ERC-4337 paymaster compatibility; ccip.rs cross-chain; solana.rs Ed25519 parity; retry.rs dead-letter; ops.rs emergency controls/kill switch.; Web3 settlement artifacts + lifecycle: chio-web3/src/settlement.rs Web3SettlementDispatchArtifact and Web3SettlementExecutionReceiptArtifact with a 9-state lifecycle (PendingDispatch..Settled/PartiallySettled/Reversed/ChargedBack/TimedOut/Failed/Reorged), anchor-inclusion-proof + oracle-conversion-evidence reconciliation, and a completion-flow binding tying every transfer back to a governed receipt id.; Settlement automation (autonomous): chio-settle/src/automation.rs SettlementWatchdogJob (EscrowTimeout/FinalityObservation/BondExpiry) triggered by Cron/Log/CustomLogic, with duplicate suppression and operator-override; outcomes Executed/DuplicateSuppressed/DelayedButSafe/ManualOverrideRequired.; Liability/insurance market: chio-market quote_and_bind, LiabilityQuoteRequest/Response, LiabilityPricingAuthority (cross-validates an active granted CreditFacility + approved underwriting decision + capital book), claim package -> adjudication (ClaimUpheld/PartialSettlement/ProviderUpheld) -> payout/settlement instructions and receipts.; Autonomous pricing + capital optimization: chio-autonomy/src/model.rs defines AutonomousPricingDecision (Reprice/Renew/Decline/BindWithinEnvelope/ManualReview) and CapitalPoolOptimization (IncreaseReserve/DecreaseReserve/ShiftCapacity/...) gated by AutonomousAutomationMode (Shadow/Advisory/Active) and review states (AutoApproved/HumanReviewRequired/ShadowOnly/Blocked), all evidence-referential to prior signed artifacts.; External agent-commerce protocol bridges: chio-agent-web-interop/src/artifacts/ has dedicated verifiers for ap2.rs, acp_commerce.rs, x402.rs (validates resource/payment-requirements/payment-proof/settlement digests, order_id, network, asset, amount, status authorized/settled/refunded, bound chio_payment_receipt_ref), plus oauth2/mcp/a2a/openapi/spiffe/scim, all projected into a TransactionPassport evidence graph.; Multi-agent shared budget for fan-out: chio-workflow-preflight/src/types.rs WorkflowBudgetPool + WorkflowPreflightPlan (parent_task -> child_tasks) with validation that parent and every child budget_minor stays within the pool total and currency is coherent (workflow_preflight_budget_pool_exceeded). Maps directly to Orca's fan-one-prompt-across-N-agents model.; Buyer/auditor trust artifacts: chio-attest-buyer-core offline proof-package verification (claims, disclosure, issuer, oracle, revocation, trust_bundle); chio-transaction-passport produces the cross-protocol evidence graph + verifier policy that enterprise-export and agent-web-interop consume.; CLI integration seam already wired: crates/products/chio-cli (binary `chio`) depends on chio-commerce-order, chio-credit, chio-settle; has command trees for settle (chio settle status over a chio-store-sqlite DB), market, capital, credit, liability (claim-settlement-instruction-issue), buyer/treaty dispatch, a --budget-db SQLite flag, and even ships a React/Vite dashboard under chio-cli/dashboard/.
Gaps: No fiat custody execution: the capital/credit layer is simulation-first/custody-neutral by default (CapitalExecutionInstructionSupportBoundary/CapitalAllocationDecisionSupportBoundary default automatic_capital_execution_supported=false, automatic_dispatch_supported=false, external_execution_authoritative=false). Only the crypto rail (chio-settle EVM/Solana) actually moves money; ACH/Wire rails emit signed instruction artifacts that a human/external custodian must execute. There is no fiat PSP/bank connector that closes the loop.; No long-running kernel server: there is no HTTP/JSON-RPC/gRPC daemon exposing the kernel or economy crates. Integration today is in-process (embedders drive the kernel) or the `chio` CLI emitting/consuming signed JSON. An Orca (Electron/TypeScript) front end has no socket/API to call; a thin local server or CLI-bridge must be built.; Commerce-order verification is post-hoc, not a live order engine: chio-commerce-order verifies an already-assembled, SHA-256-pinned bundle (event log + payment lifecycle + mandate ledger). Nothing in-repo orchestrates a live order forward through those states, calls a real PSP to create the payment intent, or assembles the bundle; the producer side is assumed external.; Budget state is in-memory / caller-supplied: BudgetEnforcer holds counters in process memory and BudgetTree.evaluate takes a caller-supplied SpendSnapshot. There is no shared, durable, concurrency-safe budget ledger that multiple parallel agent worktrees could draft against atomically (the SQLite snapshot store is explicitly out of scope of chio-metering).; No price discovery / catalog: bidding requires a pre-existing signed Listing + ListingPricingHint (chio-listing). There is no in-repo registry service that publishes, indexes, or lets an agent search live tool/data/compute listings; chio-listing provides the types and search primitives but not a running marketplace registry.; AP2/ACP mandates are verified by hash only: chio-commerce-order checks ap2_checkout_mandate_hash / ap2_payment_mandate_hash / acp_delegated_payment_token_hash are well-formed SHA-256 and occurrence/window-consistent, but does not parse or cryptographically verify the underlying AP2/ACP mandate documents themselves (that lives partially in chio-agent-web-interop adapters but is not joined to the order replay).; No agent-to-agent payment primitive distinct from buying capabilities: an agent can buy a scoped capability token and reserve funds, but there is no first-class 'agent A pays agent B for a delivered result' settlement object outside the liability-claim-payout and capital-transfer paths; peer settlement would be assembled from capital-execution instructions by hand.; Metering is not automatically populated from real tool cost: CostMetadata (compute time, data volume, API cost) is a typed container the kernel/guards must fill; there is no built-in collector that derives actual provider cost (e.g. tokens, GPU-seconds, vendor invoice) for an arbitrary CLI coding agent run.
Opportunities: Wrap the `chio` CLI as Orca's commerce backend: Orca already shells out to CLI agents and ships an Orca CLI; fuse it with crates/products/chio-cli so every worktree action that touches a paid/metered tool routes through `chio` subcommands (settle status, capital instruction, claim-settlement-instruction-issue), surfacing signed JSON receipts in the Orca diff/review pane. No new protocol needed.; Map Orca parallel-worktrees onto WorkflowBudgetPool: when a user fans one prompt across N agents, materialize a chio-workflow-preflight WorkflowPreflightPlan (parent_task -> child_tasks) so each worktree gets a capped slice of one budget pool with currency coherence, and reject over-allocation client-side before any agent runs (workflow_preflight_budget_pool_exceeded).; Per-worktree capability wallet via chio-open-market: give each isolated git worktree its own agent subject key; the bid/ask/accept flow (chio-open-market/bidding.rs) mints a scoped, cost-capped, time-bounded CapabilityToken per worktree so an autonomous agent can buy exactly the tool access it needs and no more, visible as a 'wallet' chip in the Orca sidebar.; Live budget HUD from BudgetEnforcer/BudgetTree: expose remaining()/total_spent() and the hierarchical BudgetDecision as an Orca usage/rate-limit panel (Orca already tracks account usage), turning the existing budget crates into a real-time spend meter per agent/session/tool.; Surface the commerce-order passport in Orca's annotate-AI-diffs review: when an agent completes a purchase, render the verified CommerceOrderPassportReport (state machine + AP2/ACP mandate binding + payment lifecycle + verified_claims) inline so a human approves a cryptographically attested transaction, not a raw log line.; Design-Mode -> x402/AP2 buy button: Orca's Design Mode lets a user click a UI element; extend that to 'click to purchase this API/data' by generating a chio-agent-web-interop x402 or AP2 artifact and a chio-settle X402PaymentRequirements, letting an agent pay an external x402-priced endpoint with a Chio-attested receipt.; Crypto settlement as the first real autonomous-commerce loop: because chio-settle (feature=web3) already executes USDC escrow lock/release on EVM and EIP-3009/Circle/x402 flows, Orca can ship a working end-to-end 'agent buys, pays, settles on-chain, receipt anchored' demo without building any fiat rail, using the operator-treasury+custodian signed capital instruction as the authorization gate.; Settlement watchdog as an Orca background task / notification: wire chio-settle automation.rs SettlementWatchdogJob (EscrowTimeout/FinalityObservation/BondExpiry, duplicate-suppressed, operator-override) into Orca's existing 'notify when an agent finishes / needs you' machinery so humans are paged only on ManualOverrideRequired.; Bonded autonomy tiers gating agent spend: use chio-credit CreditBondedExecutionControlPolicy (kill switch, max autonomy tier, require locked reserve, deny on delinquency) so Orca exposes a per-agent 'autonomy dial' where higher tiers require a posted bond and a higher runtime-assurance tier before the agent may transact unattended.; Reputation/credit-scored provider picker: feed chio-credit CreditScorecard bands and chio-open-market listing SLAs into Orca's native marketplace/account-switcher UI so when an agent needs a tool, the cockpit ranks providers by signed reputation, revocation rate, and price, then auto-bids.; Differentiated moat = attested receipts + audit export: every commerce action already terminates in a signed receipt, evidence graph (chio-transaction-passport), and enterprise/SIEM export (chio-enterprise-export, evidence_export); position Chio-on-Orca as the only agent cockpit where autonomous spend is provably bounded, mandate-gated, and exportable for EU AI Act / PCI-DSS / ISO 42001 compliance.

### ground:chio-trust
The Chio trust layer is unusually complete for agent-to-agent commerce, far beyond a typical attestation framework. Agent identity is self-certifying: did:chio (crates/trust/chio-did) uses an Ed25519 public key as the method-specific id, and the same key is bound into every CapabilityToken.subject (crates/core/chio-core-types/src/capability/token.rs) as a DPoP sender constraint, so identity, delegation, and authorization share one key with no registry lookup. On top of that sits a full verifiable-credentials lane (chio-credentials): native Ed25519-signed AgentPassports plus a standards-native OID4VCI/OID4VP projection, cross-issuer portfolios, selective disclosure via BBS+ (chio-selective-disclosure), and a TrustTier (Unverified/Attested/Verified/Premier) synthesized from compliance score and behavioral anomaly. Reputation (chio-reputation) is deterministic and receipt-derived: eight behavioral metrics composed into a Sybil-resistant tier mapping with per-feed floors. Every kernel decision is signed into a ChioReceipt that already carries rich FinancialReceiptMetadata (settlement status, budget holds, delegation depth, root budget holder, oracle conversion evidence), and bilateral cross-org co-signing (chio-federation DualSignedReceipt) plus an offline buyer/auditor proof-verification boundary (chio-attest-buyer) provide non-repudiation across kernels. Commerce is partly built already: a chio-commerce-order crate validates AP2 checkout/payment mandate hashes and ACP delegated-payment tokens, chio-settle implements x402 (EIP-3009 transfer-with-authorization), and chio-market ships a complete liability-claim -> dispute -> adjudication lifecycle. The main missing pieces are legal-entity binding (KYC/identity-proofing of agents), sanctions/AML screening, hardened escrow, neutral-arbiter binding for disputes, and any UI/CLI surface to expose counterparty trust. Revocation is handled by a sparse-Merkle revocation oracle (chio-revocation-oracle) with non-inclusion proofs and a passport bridge.
Capabilities today: Self-certifying agent identity: did:chio (crates/trust/chio-did/src/lib.rs) where the method-specific id is the lowercase hex of an Ed25519 public key; resolution is registry-free and self-certifying, with optional ChioReceiptLogService and ChioPassportStatusService endpoints on the DidDocument.; Identity-to-authorization binding: CapabilityToken.subject and CapabilityTokenBody.subject are PublicKey (crates/core/chio-core-types/src/capability/token.rs), bound as a DPoP sender constraint, so the did:chio key is also the capability holder; tokens carry issuer, scope, delegation_chain (Vec<DelegationLink>), caveats, and budget_share_bps for sub-agent budget splits.; Verifiable credentials and Agent Passport: chio-credentials ships AgentPassport (passport.rs) as a bundle of Ed25519-signed ReputationCredentials with merkle_roots, valid_until, PassportLifecycleState (Active/Stale/Superseded/Revoked), and a standards-native OID4VCI/OID4VP lane (oid4vci.rs, oid4vp.rs, portable_jwt_vc.rs, portable_sd_jwt.rs) plus cross-issuer portfolios/trust-packs/migration (cross_issuer.rs).; Coarse trust gating: TrustTier (crates/trust/chio-credentials/src/trust_tier.rs) deterministically maps a 0..1000 compliance score plus behavioral-anomaly flag into Unverified/Attested/Verified/Premier, with a monotone, fail-pessimistic rule that a live anomaly blocks promotion to Premier; relying parties gate on this without parsing the full factor breakdown.; Deterministic, receipt-derived reputation: chio-reputation computes a LocalReputationScorecard (score.rs) from a LocalReputationCorpus of signed receipts, capability-lineage records, and budget usage, across eight metrics (boundary pressure, resource stewardship, least privilege, history depth, specialization, delegation hygiene, reliability, incident correlation); receipt_integrity_valid enforces trusted_kernel_keys so unsigned receipts score zero.; Sybil-resistant reputation tiers: ReputationTier (crates/trust/chio-reputation/src/tier.rs) requires composed-score thresholds AND a per-feed floor (TIER_3_PER_FEED_THRESHOLD) so a flood of one feed cannot reach the top tier; tiers gate marketplace discovery visibility while cosign verify gates publication.; Signed, economically-aware receipts: ChioReceipt (crates/core/chio-core-types/src/receipt/body.rs, schema chio.receipt.v1) is content-addressed, carries actor_chain, GuardEvidence, policy_hash, and trust_level, and FinancialReceiptMetadata (receipt/economics.rs) records cost_charged, currency, budget_remaining/total, delegation_depth, root_budget_holder, payment_reference, SettlementStatus, oracle_evidence, plus full budget-hold lineage (authorize/terminal exposure and realized spend).; Cross-org non-repudiation: chio-federation bilateral co-signing (bilateral.rs) produces a DualSignedReceipt where both org A and org B kernels sign the canonical CoSigningBody over the same receipt bytes; verification is strict (both signatures must validate against pinned peers). Kernel-to-kernel trust is established via a signed mTLS-style handshake that pins peer keys with a rotation_due freshness ceiling (trust_establishment.rs).; Offline buyer/auditor proof verification: chio-attest-buyer exposes a fail-closed verification boundary (api.rs verify_buyer_attestation_packet / verify_buyer_attestation_review_package_with_proof_replay_json) over BuyerAttestationPacket and ReceiptLineageBundle (types.rs), binding buyer_id, capability_id, treaty scope, BilateralInvocation, workflow receipt, budget_refs, and settlement_claimed into a replayable proof package.; Hardware/TEE attestation: chio-attest-verify is the single source of truth for Sigstore (Fulcio chain, OIDC issuer pinning, SAN regexp, Rekor inclusion + SET) and TEE quote verification for Nitro, SEV-SNP, and TDX (nitro.rs, sev_snp.rs, tdx.rs), all fail-closed with unwrap/expect/unsafe forbidden at the lint level; chio-tee runs a signed, redacted shadow-capture sidecar.; Revocation with proofs: chio-revocation-oracle provides epoch-signed sparse-Merkle roots with InclusionProof/NonInclusionProof, a freshness verifier, and a passport_bridge (apply_passport_revocation) so passport/credential revocation is provable and bounded by epoch freshness.; Capability leases / mandates: chio-governance CapabilityLeaseArtifact (lease.rs, schema chio.capability-lease.v1) is a signed issuer->subject grant over a scope_digest with an action class (ScopedObservation, DelegatedAction, NarrowDestructive) and validity window, verified by verify_capability_lease.; Existing commerce primitives: chio-commerce-order (crates/platform/chio-commerce-order) validates a CommerceOrderContext (buyer/agent/merchant subjects, quote, hashed event log + payment lifecycle + mandate ledger) and a CommerceMandateLedger binding ap2_checkout_mandate_hash, ap2_payment_mandate_hash, and acp_delegated_payment_token_hash with single-use/occurrence and max-amount allowance enforcement.; On-chain settlement rails: chio-settle implements x402 (payments.rs: X402PaymentRequirements, X402SettlementMode PrepaidAuthorization/EscrowBacked, EIP-3009 TransferWithAuthorization with domain separator) and chio-web3 carries settlement_proof.rs with PublicSettlementDisputeSnapshot/Context and a Web3DisputePolicy::OffChainArbitration / Arbitrator role.; Dispute and adjudication lifecycle: chio-market/src/claim.rs ships SignedLiabilityClaimResponse (Accepted/Denied/partial with covered_amount), LiabilityClaimDisputeArtifact (opened_by, reason, evidence_refs), and LiabilityClaimAdjudicationArtifact (adjudicator, outcome, awarded_amount); chio-control-plane/src/certify.rs adds CertificationDisputeState/Record/Request.; Differentiated trust signal: chio-pheromone is a signed, Merkle-committed stigmergic substrate (PheromoneDeposit, observation-cost commitments, scarcity policy, newcomer discount horizon, runtime trust-floor state) gossiped across operators via chio-federation pheromone_gossip, giving a decentralized emergent-trust channel distinct from credential/reputation scoring.; Enterprise identity provenance: EnterpriseIdentityContext / EnterpriseFederationMethod (Jwt, Introspection, Scim, Saml) in crates/core/chio-core-types/src/session.rs lets a passport record enterprise_identity_provenance, tying an agent session to a corporate IdP.
Gaps: No KYC-of-agents / legal-entity binding: did:chio and passports prove key control and behavior, but nothing binds an agent key to a verified legal person or organization (no identity-proofing credential type, no LEI/EIN/business-registration attestation). EnterpriseIdentityContext links to a corporate IdP but is not a KYC artifact and is unverified provenance metadata.; No sanctions / AML / counterparty-screening primitive anywhere in crates/trust or crates/economy: no sanctions list, no jurisdiction/eligibility gate, no travel-rule data. Commerce can be metered and settled but not compliance-screened against a counterparty allow/deny policy.; Counterparty trust is verifiable but not discoverable: there is no agent-to-agent counterparty directory or trust-lookup surface. A relying agent can verify a presented passport/receipt, but nothing helps it find a counterparty, fetch its current TrustTier/reputation, and negotiate terms before transacting.; Dispute adjudication has no neutral-arbiter binding: LiabilityClaimAdjudicationArtifact.adjudicator and Web3RegulatedRole::Arbitrator are free-form identifiers; there is no registry of trusted arbiters, no escrow-release-on-adjudication wiring, and no enforced link from a signed adjudication outcome back to a settlement reversal/refund.; Escrow is declared, not implemented: X402SettlementMode::EscrowBacked and EscrowBacked dispute policy exist as enum variants, but there is no escrow state machine (lock, hold-until-delivery, release/refund) tying budget holds in FinancialReceiptMetadata to on-chain escrow in chio-settle/chio-web3.; No portable mandate <-> capability bridge surfaced: chio-commerce-order validates AP2/ACP mandate hashes and chio-governance issues capability leases, but they are separate artifacts; there is no single helper that turns a verified AP2/ACP payment mandate into a scoped, budget-bounded CapabilityToken the kernel will enforce at tool-call time.; Reputation is local-corpus-only by design: compute_local_scorecard depends on the caller assembling a corpus; there is no shared/queryable reputation service or signed reputation-snapshot exchange protocol for a counterparty to pull a fresh score at transaction time (portable_reputation.rs is a credential format, not a live feed).; No product surface: all of the above lives in Rust crates with no CLI/UI exposure. There is no Orca-side panel, command, or wire endpoint to issue a passport, present credentials, view a counterparty trust tier, open a dispute, or inspect a settlement receipt - the forked cockpit would need this entire presentation layer.
Opportunities: Counterparty trust card in the forked Orca worktree/agent view: when one agent is about to transact with another tool server or agent, render a trust card backed by chio-credentials AgentPassport verification + TrustTier + chio-reputation tier and a chio-revocation-oracle freshness check; gate the transaction in the kernel on a verifier policy (PassportVerifierPolicy from chio-credentials/registry.rs). This is the headline 'agents you can trust to transact' surface and is mostly assembling existing verified data.; Mandate-to-capability minting: add a control-plane helper that converts a verified chio-commerce-order CommerceMandateLedger (AP2 checkout/payment mandate, ACP delegated-payment token) into a scoped, budget-capped CapabilityToken with budget_share_bps and a CapabilityLeaseArtifact, so a signed human/AP2 mandate becomes kernel-enforced spend authority. Surface it as an Orca CLI command (e.g. chio mandate grant) and a 'budget granted' chip in the UI. Differentiated because the mandate is cryptographically the same key that pays and that the kernel meters.; Signed settlement receipts in the diff/review pane: extend Orca's annotate-AI-diffs review to attach the ChioReceipt + FinancialReceiptMetadata (cost_charged, root_budget_holder, SettlementStatus, oracle_evidence) and, for cross-org calls, the DualSignedReceipt, so every paid tool call an agent made shows a verifiable cost-and-settlement line. chio-attest-buyer already gives an offline verify path for an auditor to replay the whole bundle.; Escrow-backed agent-to-agent jobs: implement the missing escrow state machine on top of the existing X402SettlementMode::EscrowBacked and EIP-3009 prepared transfers, releasing funds only against a co-signed delivery receipt (chio-federation bilateral co-sign) and refunding against a signed LiabilityClaimAdjudicationArtifact. This closes the loop between chio-market dispute artifacts and chio-settle/chio-web3 settlement and is highly defensible (capability-gated escrow with cryptographic delivery proof).; Neutral-arbiter registry and one-click dispute: bind LiabilityClaimAdjudicationArtifact.adjudicator to an arbiter identity attested via chio-attest-verify (Sigstore/TEE) and listed through chio-federation, then expose 'open dispute' from the Orca receipt view to emit a SignedLiabilityClaimDispute with evidence_refs pulled straight from the receipt/lineage bundle. Turns the existing dispute types into an end-to-end, non-repudiable resolution flow.; KYC-of-agents credential type: add a new ReputationCredential/VC subtype in chio-credentials that binds a did:chio key to a verified legal entity (issuer = a KYC provider attested via chio-attest-verify), revocable through the existing chio-revocation-oracle passport bridge, and gate high-value transactions on its presence via PassportVerifierPolicy. This fills the single biggest gap (legal-entity binding) using the existing credential, tier, and revocation machinery.; Pheromone-based emergent counterparty trust: use chio-pheromone deposits and concentration plus chio-federation pheromone_gossip to surface a live, decentralized 'is this tool server / agent currently trusted by the swarm' signal in the Orca fleet view, complementing static credentials with real-time behavioral consensus across operators - a genuinely differentiated trust channel competitors lack.; Portable reputation handshake at deal time: define a signed reputation-snapshot request/response (extending portable_reputation.rs) so a counterparty agent can pull a fresh, integrity-checked LocalReputationScorecard summary before transacting, exposed via the protocol adapters (chio-a2a-adapter / chio-mcp-adapter) so external agents over A2A/MCP can request Chio trust attestations as a paid, metered tool.

### ground:orca-fork-surface
Orca (github.com/stablyai/orca, owned by Lovecast Inc., MIT-licensed, ~4.8k stars) is a large but cleanly-layered Electron + TypeScript desktop app (40.6MB TS, ~5,120 files) plus an Expo/React-Native mobile companion (iOS Swift + Android Kotlin native audio module). It is an "ADE" that runs any CLI coding agent (Claude Code, Codex, Gemini, Cursor, Copilot, OpenCode, etc.), each in its own git worktree, with parallel orchestration, Ghostty-class WebGL terminals, an embedded Chromium "Design Mode," native GitHub/Linear/GitLab/Jira browsing, SSH worktrees, and computer use. ### ground:regulatory
Autonomous-agent commerce sits on a payments stack built for humans, and that mismatch is the central design constraint. Custody is the bright line: hold or move user funds and you are a money transmitter (FinCEN MSB plus state MTLs, unlicensed is a felony under 18 U.S.C. 1960, 50-state licensing about 250k-350k), while genuine non-custodial software is not. Stablecoins are now regulated (US GENIUS Act enacted July 18 2025, EU MiCA) with 1:1 reserves, restricted issuance and custody, and no yield, and KYC and AML assume a human principal an agent cannot be. Card networks (Mastercard Agent Pay, Visa Trusted Agent Protocol) ship verified-agent rails but agent chargeback and dispute liability is explicitly unsettled and networks will not absorb losses they did not authorize. The lowest-friction legal path stays out of the flow of funds with a licensed custody and KYC partner, settles over regulated stablecoin or card rails, and enforces signed spending mandates with full audit trails so a regulated principal is always accountable.</summary>

## Red-team digest (6 critics)

### Technical feasibility: fusing a 122-crate Rust protocol into a forked 40MB-TS Electron app, maintained by a small team
Fatal flaws: Hot-path FFI cannot enforce spend. The entire 'kernel refuses the next paid call' / anti-$47k-runaway pitch rests on BudgetEnforcer, which lives in chio-metering and is NOT in the FFI dependency closure (chio-core + chio-manifest only). The 14 extern-C functions are stateless verifiers (canonicalize, sha256, ed25519 sign/verify, verify capability/receipt/manifest JSON) with zero mint/budget/settle/escrow/approval/disburse. So budget enforcement on the agent-hooks bus MUST be an async localhost round-trip to the sidecar, not the advertised 'sub-millisecond zero-IPC' in-process call. The bridge brainstorm conflates 'verify a token locally' (FFI can) with 'check spend against a running budget' (sidecar only). This is recoverable but invalidates the headline latency story.; The 'live USDC on-chain in 30 seconds, rests on shipped code' demo is not shippable from this repo as-is. chio-settle is #![cfg(feature=\"web3\")] and its functions are prepare_transfer_with_authorization / prepare_* (artifact emitters). chio-credit/capital_and_execution is hardcoded simulation_first_only=true, external_execution_authoritative=false, automatic_capital_execution_supported=false. Nothing in-tree broadcasts a signed tx to a chain. A real testnet loop needs a separate signer + RPC broadcaster + key custody the team must build and operate, plus the full alloy EVM dependency stack. Several lenses present this loop as turnkey; it is not.; Fork-maintenance math is unbudgeted and underestimated. Orca ships daily and the plan rebrands ~56 brand paths + appId + bin shims while threading commerce:* IPC, a koffi FFI loader, ported dashboard, and (per some lenses) Swift/Kotlin UniFFI into a fast-moving upstream. Rebranded strings collide with upstream churn on nearly every rebase; the mobile-companion UniFFI path doubles the surface across three languages. With no stated rebase cadence or a thin chio-orca product-crate boundary actually built yet, a small team spends its capacity on merge conflicts, not features.
Must-haves: Build a real chio-orca + chio-orca-core product crate FIRST (mirroring the existing chio-mercury/-core and chio-wall/-core template) so 100% of Orca-specific Rust and the commerce:* request/response schemas live in this repo, versioned with the protocol and behind the public_entrypoint allowlist. ### Legal, payments & licensing (money-transmission/MSB, KYC/AML, custody, stablecoin/card-network rules, fork license/trademark/attribution)

### Security & abuse surface (unauthorized spend, fraudulent billing, mandate bypass, key theft, money laundering)
Fatal flaws: No AML / sanctions / Travel-Rule / KYC primitive exists in the codebase (grep across all crate src returns zero hits for AML, OFAC, sanctions, launder, travel-rule, KYC). Saturating arithmetic prevents overflow but not double-spend: Orca's defining feature is fanning one prompt across N parallel agent processes, and the brainstorm sells 'Fan-Out Wallet Race: One Budget, Five Agents, Atomic' - but nothing in the inspected enforcer provides the atomic shared-balance reservation that claim requires. Two worktrees checking the same pool concurrently both pass. Hot-path verification via koffi/FFI in Electron main PLUS stateful settlement via the axum sidecar means there are two code paths to 'allow'. The brainstorm even flags that chio-api-protect has advisory routes (/v1/evaluate/advisory sets authorization:false); mis-wiring an advisory verdict as enforcement is a documented foot-gun and silently turns the kill switch into telemetry.
Must-haves: Single authoritative spend ledger with atomic reserve-then-charge. Per-worktree/per-process BudgetEnforcer instances are advisory caches only. Without this, fan-out double-spend defeats every budget claim. The WorkflowBudgetPool preflight (chio-workflow-preflight) validates allocation but is not a runtime reservation - it must be backed by atomic mint at call time.; Fail-closed-by-construction approval: governed/over-threshold intents with no valid ApprovalToken DENY, never proceed. The Option<GovernedApprovalToken> in runtime.rs must resolve to a hard reject for any intent above the autonomy/amount threshold. Pair with execution_nonce binding (already shipped) so an approval for call A cannot authorize call B.; Sanctions/Travel-Rule screening as a kernel guard at mint AND settle, fail-closed. Before any CapabilityToken that authorizes payment is minted and before chio-settle emits a settlement instruction, the counterparty did:chio (and its KYA-bound legal entity, once that actually exists) must clear a sanctions/denied-party check. This crate does not exist today and is non-negotiable before any real-value rail ships. Fail-closed: unscreened or unreachable-screening-oracle denies.; Hardware-bound, non-exportable approver keys with a server that cannot forge approvals. The chio-custody-hw App Attest / passkey path (verify_app_attest, pinned APPLE_APP_ATTEST_ROOT_SHA256, counter enforcement) must be the ONLY source of the trusted_approvers key material for high-value tiers, and the Orca server/desktop/CI must never hold approver signing material. Best-surviving ideas: Secure-Enclave approver key (Mobile lens) and Approve-The-Spend-With-Your-Thumb (Demo lens): survives best. chio-custody-hw genuinely ships App Attest / Play Integrity / passkey verification with pinned roots and counter enforcement, and the kernel's trusted_approvers + parameter_hash binding makes 'the server literally cannot forge an approval' a true statement, not marketing. # Chio Lean Wedge: "The runaway-agent kill switch you can audit"

## One-line thesis

Every other agent cockpit shows you what your fleet spent; Chio-on-Orca is the only one that **refuses the next paid call when the budget is blown** and hands you a **signed, replayable receipt** to prove it - enforcement that lives outside agent code, in the kernel, not the prompt.

## The wedge and the first customer

**Wedge:** A hard, kernel-enforced spend ceiling on Orca's parallel agent fan-out, with a per-prompt budget pool and a signed receipt per run. One sentence to a buyer: *"Set a budget pool, fan one prompt across N agents, and your agents physically cannot exceed it - here is the signed receipt you give the client."*

**First customer:** The 5-to-50-person **AI-native dev shop or agency that runs parallel CLI agents on client money** and bills compute/API spend back. They feel both acute pains at once: runaway-overspend risk (the cited $47k LangChain incident is their nightmare) and prove-what-we-billed (every client invoice is an argument). This ICP is narrow enough to dominate by word of mouth in the Orca/Claude Code community and broad enough to expand from.

**What we charge for, today:** A seat-plus-usage governance license (priced per worktree-seat and per attested run), and a flat compliance/audit-export add-on for the first agencies that resell to regulated clients. We price as **governance and observability software, never as a payments take-rate.** The revenue model must not depend on agent-to-agent settlement volume existing in 2026, because it does not.

## Top features (each tied to a Chio crate and an Orca surface)

1. **Hard per-worktree spend mandate that fails the next paid call closed.** A signed spend cap per worktree/agent; when a metered call would breach it, the kernel denies fail-closed and pauses the worktree, rather than a dashboard merely warning after the money is gone.
   - *Crate:* `chio-metering` (`BudgetEnforcer`/`BudgetPolicy`, saturating arithmetic, typed `BudgetViolation`) backed by `chio-credit` `CreditBondedExecutionControlPolicy` (`kill_switch`).

2. **Per-prompt fan-out budget pool, pre-rejected before any agent runs.** When the user fans one prompt across N agents, each worktree draws a capped, currency-coherent slice of one signed pool; over-allocation is refused client-side at preflight.
   - *Crate:* `chio-workflow-preflight` (`WorkflowBudgetPool`/`WorkflowPreflightPlan`, `workflow_preflight_budget_pool_exceeded`).
   - *Orca surface:* The fan-one-prompt-across-N launch dialog gains a "Budget pool" field; the worktree grid header shows a shared-pool gauge and each card its remaining slice. This is the cleanest one-to-one fit to Orca's signature UX.

3. **Signed IOU and receipt per run, rendered in the review pane.** Every metered call mints a signed IOU bound to the receipt's content and policy hashes; zero-price calls skip minting. The bill cannot be detached from what happened.

4. **Authoritative spend ledger via the bundled `chio-api-protect` sidecar.** A single process holds funds-reserved state and is the only path to spend; per-worktree enforcers are advisory caches. This is what makes "physically cannot overspend" true across N parallel worktrees rather than a per-process lie.
   - *Crate:* `chio-api-protect` (finished axum control plane; `/chio/evaluate`, `/v1/capabilities/mint` and `/release`, `/approvals/*`).

## What we deliberately do NOT build

- **No custody, no wallet, no fund movement in the default product.** Chio prepares and proves; a licensed rail moves money. The web3/`chio-settle` broadcast path stays feature-gated, off by default, and is at most a later regulated-operator add-on SKU. We never bundle an operator signing key in the distribution.
- **No settlement take-rate.** Charging basis points on the flow of funds is the single most license-triggering decision available and contradicts the custody-neutral architecture. We price as SaaS (seat + usage) and an enterprise compliance license.
- **No two-sided marketplace in v1.** No Bazaar, no list-to-sell wizard, no federated registries, no bonded-seller slashing, no agent-to-agent hiring. These are cold-start traps that need buyer and seller liquidity that does not exist; they are a year-two option the wedge must earn first.
- **No live on-chain "buy the API" demo as the headline.** It is prepare-only in-tree and needs a broadcaster and testnet ops nobody has budgeted. We keep it as an internal proof of the rail-neutral story, not a sales demo.
- **No KYC/AML/sanctions product we cannot back.** We are strictly a relying party. If counterparty screening is ever needed, the licensed issuer carries the BSA/CIP obligation and liability; Chio verifies, it does not warrant identity. (And because v1 moves no money, this surface stays out of scope entirely.)
- **No autonomous, unattended buying.** v1 is enforcement and audit of agent spend under human-set mandates, not agents transacting unattended on the open market.
- **No FFI-based spend gate.** The FFI surface (`chio-bindings-ffi`) is stateless verify/sign/hash only. Budget enforcement is stateful and lives behind the sidecar. We use FFI only for offline signature/canonicalization checks on the read path, never to authorize a call.

## Top risks and mitigations

### Risk 1: The headline enforcement claim is false in Orca's signature topology (fan-out double-spend)
`BudgetEnforcer` is an in-memory, single-process, non-atomic counter. Across N parallel worktrees, two agents checking the same pool concurrently both pass, so "physically cannot overspend" is not true in exactly the configuration the product runs in. This is the single most dangerous gap because it is a marketed feature that the code does not deliver as-pitched.
- **Mitigation:** Make the bundled `chio-api-protect` sidecar the one authoritative reservation service. Every paid call must obtain a scoped capability via an atomic reserve-then-charge against a durable, concurrency-safe ledger before execution; per-worktree enforcers are advisory caches only. The `WorkflowBudgetPool` preflight validates allocation but must be backed by atomic mint at call time. Do not ship the kill-switch claim until a single-ledger reservation path is demonstrated under concurrent fan-out. Treat this as the first hard engineering milestone.

### Risk 2: Demand for "agents transacting" is premature; we could build for a market that is not buying yet
If we drift toward marketplace, settlement, or autonomous-buying features, we are underwriting a 2027 thesis with a small team and will starve the one thing customers buy now.
- **Mitigation:** Lead with control and compliance, not commerce. The sellable unit this quarter is the budget pool plus the signed receipt; the expansion is the audit-export and SIEM license. Validate with 2-3 named design-partner agencies running fleets on real budget who will pay for the brake and the receipt before any spend on marketplace surfaces. Cut every feature whose unit economics depend on agent-to-agent transaction volume materializing. The contrarian "sell the NO" framing (prove the agent did less than authorized) is both the safest positioning and the one matching the prepare-only code.

### Risk 3: The fork is a maintenance treadmill and the moat lives in code that is MIT and copyable
Orca ships daily across ~5,000 files; a naive fork drowns a small team in rebase conflicts. Separately, both the cockpit (MIT) and the protocol crates are forkable, so a well-funded incumbent could copy the surface. The durable moat is not the receipt format or the kill switch (each a one-quarter bolt-on) but architectural neutrality plus an accumulated, signed audit history a fork cannot mint.
- **Mitigation (fork):** Build a versioned `chio-orca` + `chio-orca-core` product crate first (mirroring the existing `chio-mercury`/`chio-wall` template) so all Orca-specific Rust and the `commerce:*` IPC schemas live in this repo behind the public-entrypoint allowlist. The Electron fork carries only brand strings, one `src/main/ipc/commerce.ts`, and the ported `chio-cli` React dashboard (React 18 + Vite -> Orca's React 19 + Vite is a minor skew). Pin to an Orca tag, rebase on a fixed weekly cadence, and isolate all rename churn into a scripted, re-runnable brand codemod so a rebase is "re-apply patch," not "resolve 200 conflicts." Retain the Lovecast Inc. MIT notice in every kept file; only net-new Chio files carry fresh copyright; drop the `Orca`/`Stably` marks and the `com.stablyai.orca` appId and run a clearance search on "Chio."
- **Mitigation (moat):** Anchor the durable defensibility in the offline-verifiable, clause-mapped compliance export (years of compliance engineering an agent-IDE incumbent will not prioritize, and counter-incentivized for any single rail that does not want its logs independently re-verifiable) and in the federation substrate (`chio-federation`, the deepest part of the codebase) as the year-two network play. Keep the operator receipt-signing trust root a service Chio runs, not a binary anyone compiles.
