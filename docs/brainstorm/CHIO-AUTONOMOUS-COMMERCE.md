# Chio: The Spend Control Plane for Autonomous Agents
### The runaway-agent kill switch you can audit

## 1. Thesis

Fork Orca (the MIT cockpit for running fleets of parallel CLI coding agents) and fuse it with the Chio protocol to ship the one thing no agent runner and no payment rail has: out-of-agent, fail-closed spend enforcement plus a cryptographically replayable receipt for every dollar an agent was authorized to move and every dollar it actually did. We sell the brake and the audit trail, not a wallet. Concretely: a hard per-worktree and per-fan-out budget mandate that the kernel refuses to exceed before any money moves, terminating in a signed, offline-verifiable receipt a developer hands their client and a CISO hands their auditor. Chio never custodies or transmits funds (the code is custody-neutral and simulation-first by construction, which is both the legal shield and the honest scope), so a licensed rail moves money later if ever. The wedge lands with AI-native dev shops burning client API budgets today; it expands into the regulated enterprise that needs provable agent governance; and it earns the right, only after that installed base exists, to become the neutral cross-rail verifier and federated trust mesh the whole agent economy will route through.

## 2. Why now

The timing is asymmetric, and being honest about which half is real is the whole game.

- **The half that is NOT ready: agents transacting as an economy.** Agent-to-agent settlement over x402/ACP/AP2 is nascent. A "take-rate on the agent economy" business is basis points of a near-zero base in 2026, and a two-sided tool marketplace is a 2027+ cold-start with no supply and no demand on day one. Any plan underwritten on that volume is a narrative.
- **The half that IS acute right now: runaway spend and prove-what-we-billed.** Teams already run many CLI agents in parallel (Orca's actual product-market signal) and already bill compute and API spend to clients or controlled budgets. The cited "$47k runaway LangChain agent with dashboards but no kill-switch" is their lived nightmare. The entire market, across every grounding source, openly admits the same unfilled white space: **enforcement must live OUTSIDE agent code**, and **there is no accepted audit-trail standard for AI-generated logs** (code-based authorization trails are untested before courts and regulators). AP2, ACP, and x402 each define authorization and payment artifacts but explicitly do NOT revoke or refuse at execution time.
- **Why Chio specifically, why now.** That white space maps almost one-to-one onto what is already built and tested in this repo: a fail-closed kernel mediating every tool call, capability tokens, a Merkle receipt log, hierarchical budget enforcement, signed IOUs per receipt, an offline buyer-side verify path, and an axum control-plane sidecar. Orca is MIT, forkable, and ships the exact parallel-fan-out UX the budget primitive was built for. The fragmentation of the payment standards is itself a closing window: nobody yet owns the neutral verifier above all three, and the architectural position is incentive-incompatible for the rails to occupy themselves.

The move is to sell the brake and the audit trail into a market that is buying control THIS year, and treat settlement and marketplace as a later option we are positioned for but do not bet the company on.

## 3. What we fork and what we add

**We fork:** Orca (github.com/stablyai/orca, Lovecast Inc., MIT). An Electron 42 + React 19 + TypeScript cockpit (~5,120 files) that runs any CLI coding agent in its own git worktree, with parallel fan-out, Ghostty-class terminals, an embedded-Chromium Design Mode, and an Expo mobile companion. Four clean process seams make it an ideal host: the main/renderer IPC hub (`src/main/ipc/register-core-handlers.ts`), the token-authed Unix-socket terminal daemon (the precedent for a Rust sidecar), the public `orca` CLI JSON-RPC transport, and the agent-hooks bus (`src/main/agent-hooks/`) that fires on every agent tool call.

**We add, and we route through ONE new `commerce:*` IPC namespace plus `orca commerce ...` CLI verbs:**

- **The enforcement spine:** `chio-metering` (`BudgetEnforcer`, `BudgetTree` for org -> dept -> team -> agent caps), `chio-credit` (`CreditBondedExecutionControlPolicy` kill switch; `CreditEvaluatorHook` minting signed IOUs), `chio-workflow-preflight` (`WorkflowBudgetPool` for fan-out), `chio-core-types` (`ChioReceipt`, `FinancialReceiptMetadata`).
- **The transport:** `chio-api-protect` (the finished axum control plane: `/chio/evaluate`, `/v1/capabilities/mint` and `/release`, `/approvals/*`) spawned as a bundled, token-authed sidecar exactly like Orca's terminal daemon. `chio-bindings-ffi` (pinned ABI v1, JSON in/out) via koffi for offline signature and hash checks on the read path only.
- **The proof surface:** the existing `chio-cli/dashboard` React/Vite components (`ReceiptTable`, `BudgetSparkline`, `DelegationChain`) ported into the renderer; `chio-cli` `cert.rs` (session compliance certificate); `chio-enterprise-export` and `chio-siem` for audit export and OCSF streaming.

**We add it correctly with a product-crate boundary:** a versioned `chio-orca` + `chio-orca-core` crate pair (mirroring the shipped `chio-mercury`/`chio-wall` template) holds 100% of Orca-specific Rust and the `commerce:*` schemas behind the public-entrypoint allowlist, so the Electron fork carries only brand strings, one `src/main/ipc/commerce.ts`, and the ported dashboard. This is what makes the daily-shipping upstream rebaseable instead of a treadmill.

## 4. The wedge

**First customer (land):** the 10-75 person **AI-native dev shop or product team running parallel CLI-agent fleets on client money.** The economic buyer is a head of engineering or a fractional controller. They feel two pains at once: an agent can torch the month's API budget in an afternoon, and they cannot prove to a client what was spent on what. The deal is a per-seat-plus-usage SaaS line approved this quarter, and the ICP is narrow enough to win by word of mouth in the Orca/Claude Code community.

**First use case:** a developer fans one prompt across N agents against a fixed budget pool, the agents run, and the fleet provably cannot exceed the pool; every run exports as a signed receipt for the client invoice.

**What we sell first:** the smallest valuable unit is **the per-prompt budget pool field on fan-out** plus a **hard per-worktree spend mandate**, with the **signed receipt per run** as the deliverable proof. That is the entire v1 pitch: *"Set a budget pool, fan a prompt across N agents, your agents physically cannot exceed it, and here is the signed receipt you give the client."*

**Expansion (land-and-expand into the real margin):** the CISO/CFO at a regulated enterprise (financial services, healthcare, regulated SaaS) moving agents from PoC to production, who buys the **compliance and audit-export license** because EU AI Act, ISO 42001, SOC 2, and PCI-DSS timelines are live and there is no audit-trail standard for AI logs.

## 6. The killer demo

**"The $47K Runaway, Stopped Mid-Keystroke, With a Receipt."** Ninety seconds, one screen, no money rail, nothing that depends on broadcasting a transaction. Provably true against shipped code.

1. The operator fans one prompt across five worktree-agents and sets "Budget pool: $50" in the launch dialog. The grid shows five cards, each with a remaining-slice chip. An attempt to spawn a sixth, over-allocated agent is **rejected at preflight** with the typed `workflow_preflight_budget_pool_exceeded` error, before any agent runs.
2. The agents run. The repurposed usage panel is now a live spend bar climbing per metered tool call.
3. One agent, told to be aggressive, races toward its slice. At the ceiling, the kernel **denies the next paid call**. The agent's terminal split shows a typed `CreditBondedExecutionDecision::Deny` finding code; the spend bar stops. The money never moved, because enforcement is outside the agent, not in its prompt. The denial is a signed, replayable artifact, not a log line.
4. The operator opens the Attested Receipts tab. Every call is a line with `cost_charged`, an IOU id, and the stamped `policy_hash`. They click "Verify offline" on one; it re-verifies the signature with no running Chio node.
5. They merge the winning worktree. A "Session Certified" badge appears, and "Export Audit Package" downloads a signed bundle ready to hand an auditor.

The line: **every other cockpit shows you the spend; Chio refuses it, and hands you the receipt.**

**The demo we deliberately do NOT lead with:** "click-to-buy-the-API, settled on-chain in 30 seconds." The code is unambiguous: `chio-settle` is `#![cfg(feature = "web3")]`, its EVM entrypoints are all `prepare_*` (the `eth_sendTransaction` call sits inside `prepare_*`), and the credit layer is `simulation_first_only=true`. Nothing in-tree broadcasts. Leading with a live-money demo invites a credibility-destroying "it does not actually settle" discovery and drags us across the money-transmitter line. We keep the on-chain escrow loop as a feature-flagged, internal, testnet-only proof of the rail-neutral story, never the headline and never a revenue dependency.

## 7. Business model

**We price as governance and security software, never as a payments take-rate.** The unit economics must not depend on agent-to-agent settlement volume existing.

- **Per-seat + usage SaaS (land):** priced per worktree-seat and per attested run, billed straight out of `chio-metering` `BillingExport`/`CostQuery`, which is value-neutral. The invoice is itself derived from signed receipts, so it is provable, a thing no other cockpit can claim.
- **Enterprise compliance and audit-export license (expand, the real margin):** a flat license for the offline-verifiable, clause-mapped evidence package, SIEM streaming, and continuous tamper-evidence monitoring. This is the SKU a regulated buyer actually has budget for in 2026, and it touches no money so it triggers no money-transmission analysis.
- **Bonded-autonomy and higher-tier features (future upsell):** higher unattended-autonomy tiers gated by a posted bond and an attested runtime tier (`CreditBondedExecutionControlPolicy` + `chio-attest-verify`). A natural revenue ladder, but downstream of trust we have not yet earned.

**What we explicitly refuse to monetize:** a settlement take-rate. Skimming 30-50 bps while in the flow of funds is the single most license-triggering decision in the entire idea space (receiving compensation for directing the movement of value is the textbook definition of money transmission), and it contradicts the custody-neutral architecture that is our legal spine. If a percentage-of-value fee is ever commercially essential, it must be charged and remitted BY a licensed partner who pays Chio a flat technology or referral fee, with Chio never in control of, and never compensated as a function of, the movement of funds.

## 8. Competitive moat

Be honest about what is a wall versus a one-quarter bolt-on. The receipt format, the kill switch, the wallet, the dashboard, and a single-rail integration are each features an incumbent ships in a quarter, and several are shipping now. The durable moat is the **combination** of two things, neither of which any single-rail incumbent can occupy:

1. **Architectural neutrality plus out-of-agent enforcement.** Stripe (ACP), Coinbase (x402), Visa/Mastercard (Agentic Tokens), Google (AP2), and Skyfire (KYA) are each a single rail or SDK that runs INSIDE agent code. None can credibly verify a rival's rail without conceding it is not the universal rail, and none can put the kill switch OUTSIDE the agent because their SDK is the agent's library. An out-of-agent kernel that mediates every tool call with signed denials and verifies rivals' artifacts is an architecture they would have to rebuild from scratch and against their own incentive. Its value grows with every rail it does NOT own.
2. **A multi-operator federation mesh of signed registries with cross-operator trust gossip, plus accumulated kernel-signed reputation a fork cannot mint.** The MIT cockpit is copyable; the protocol crates are open. The only uncopyable asset is the live network and its history. `chio-federation` is verified to be the deepest part of the codebase (stake-gated open admission, pheromone and revocation gossip, bilateral co-signing, with extensive tests), and you cannot fork other operators' receipts. This is the actual wall, and it is a Year-3 asset that the wedge's installed base seeds.

The **custody-refusal stance** is the strongest moat that is true TODAY rather than contingent on a future network: it is verified in code (loopback-only settlement RPC, prepare-only EVM dispatch, `simulation_first_only=true`), and it is architectural and legal, not merely technical. Incumbents who took custody to win UX cannot un-take it without dismantling their product. The **offline-verifiable compliance export** is the most defensible enterprise moat because "hard to build" there genuinely equals "hard to compete against," and a payment rail is counter-incentivized to make its own logs independently re-verifiable by a third party.

The honest exposure: this moat is a standards-adoption and two-sided-network bet, and the rails own the distribution and the standards authorship needed to win it. We hedge by being the first and most complete cross-rail binder during the fragmentation window, and by leaning the near-term business on the compliance franchise, which is defensible even if the rails consolidate.

## 9. Top risks and how we design around them

**Risk 1 (disqualifying if unfixed): fan-out double-spend makes the headline claim false.** `BudgetEnforcer` is verified to be an in-memory, single-process, non-atomic `u64` (`total_spent`, `&mut self`, no `Arc`/`Mutex`). Across Orca's signature N-parallel-worktree fan-out, two worktrees checking the same pool concurrently both pass, so "physically cannot overspend" is untrue in exactly the topology the product runs in.
*Design-around:* the `chio-api-protect` sidecar is the SINGLE authoritative reservation service with atomic reserve-then-charge against a durable, concurrency-safe ledger. Every paid call must obtain a scoped capability via atomic mint before execution; per-worktree enforcers are advisory caches only. The `WorkflowBudgetPool` preflight validates allocation but must be backed by atomic mint at call time. This is the first hard engineering milestone, and we do not ship the kill-switch claim until no-double-spend is demonstrated under concurrent fan-out.

**Risk 2 (disqualifying if unfixed): approval is opt-in at the type level (mandate-bypass).** `ApprovalRequest.approval_token` is verified to be `Option<GovernedApprovalToken>`. With an untrusted LLM authoring tool-call requests and a prompt-injection adversary, any path that treats missing-approval as proceed-without-approval defeats the gate.
*Design-around:* invert to fail-closed-by-construction. Any governed or over-threshold intent with no valid `ApprovalToken` DENIES, never proceeds. Bind every approval to `execution_nonce` (already shipped) over the full economic envelope (amount, counterparty, currency, resource), so an approval for call A cannot authorize call B and an injected purchase cannot substitute a malicious payee after a benign approval.

**Risk 3: the fork treadmill and a mid-refactor substrate drown a small team.** Orca ships daily across ~5,120 files, and the commerce crates are mid-extraction out of `chio-control-plane` in the uncommitted working tree.
*Design-around:* land the extraction and build the `chio-orca` + `chio-orca-core` product crate FIRST so the Electron fork carries only brand strings, one IPC file, and ported dashboard components. Pin to an Orca tag, rebase weekly, and isolate all rename churn into a scripted, re-runnable brand codemod so a rebase is "re-apply patch," not "resolve 200 conflicts." Assert `CHIO_FFI_ABI_VERSION` and a sidecar `/version` handshake at startup so any drift fails closed. Retain the Lovecast Inc. MIT notice in every kept file, add Chio copyright only to net-new files, drop the `Orca`/`Stably` marks and the `com.stablyai.orca` appId, and run a "Chio" wordmark clearance search before public launch.

**Risk 4: the marketed differentiator is thinner than the marketed depth.** The cross-rail binding (`chio-commerce-order`) is verified to be three hashed mandate fields in a fixed state machine with few tests, and it verifies an already-assembled bundle rather than orchestrating a live order. A competent incumbent replicates "we hash your AP2 mandate and ACP token" in a quarter.
*Design-around:* do not sell the cross-rail verifier as the v1 wedge. Sell the brake and the receipt, where the depth (the kernel, the budget tree, the signed IOU, the federation layer) is real. Make deepening the verifier into a true cryptographic check of the underlying mandate documents the explicit Year-2 job, and anchor durable defensibility in the federation mesh and the compliance export, not the hash binding.

**Risk 5: no AML/sanctions/KYC primitive exists, and we deliberately do not build one.** A case-insensitive search across all crate sources returns zero hits; the "KYA credential" is a reputation tier, not legal-entity binding or sanctions screening.
*Design-around:* this is a non-issue precisely because v1 moves no money. We refuse custody, escrow, peer settlement, and any real-value rail in v1, which removes the entire AML surface. If a money rail is ever added, sanctions/Travel-Rule screening becomes a fail-closed kernel guard at mint AND settle, and KYC is carried by a licensed issuer who holds the BSA/CIP obligation; Chio is strictly the relying party that verifies and pins the issuer.

**Risk 6: demand is asserted from one anecdote.** One viral incident is a hook, not a market.
*Design-around:* sign 2-3 named design-partner agencies running fleets on real client budget who will pay for the budget pool plus receipts BEFORE scaling spend. If they will not pay, the "now" thesis is unproven regardless of how good the Rust is.

Do we keep the federation/reputation/receipt-signing trust root a service Chio operates rather than a binary anyone compiles, and are we willing to license the platform-tier crates defensively?
5. **Trademark and brand clearance.** Is "Chio" cleared against existing marks for software/fintech before we sink rebrand cost and a public launch into it?
6. **Enterprise-first or developer-first GTM sequencing.** The brief lands on dev shops and expands to the CISO/CFO. Given that the highest-margin, least-copyable SKU is the compliance export, is there a case to lead enterprise-first instead, accepting a longer sales cycle for a stickier, more defensible first dollar?
