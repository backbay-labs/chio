# Chio editor extensions

This directory holds the first-party Chio editor packaging for VSCode
and Zed plus the tool-neutral snippet sources both extensions consume.

| Path | Editor | Notes |
| ---- | ------ | ----- |
| [`vscode-chio/`](./vscode-chio) | Visual Studio Code | TypeScript extension, language IDs `chio-yaml` / `chio-manifest` / `chio-guard`. |
| [`zed-chio/`](./zed-chio) | Zed | Rust + wasm32 extension; on host targets builds as a plain rlib so the workspace `cargo build` exercises the manifest contract. |
| [`snippets/`](./snippets) | shared | Tool-neutral YAML sources rendered into each editor's native snippet format by `cargo xtask snippets regen`. |

Both extensions are LSP clients; they spawn the `chio-lsp` binary and
forward diagnostics, completion, hover, and go-to-definition without
re-implementing anything on the editor side. Diagnostics carry
`urn:chio:error:*` registry codes, which the editor renders verbatim.

## chio-lsp binary contract

The extensions launch the language server over stdio. The contract is:

- Binary name: `chio-lsp`. Resolved on the user's `PATH` by default.
  Both editors expose a setting (`chio.lsp.path` for VSCode,
  `chio.lsp.path` under the extension's settings table for Zed) so the
  user can pin an absolute path when `chio-lsp` is not on `PATH`.
- Transport: LSP over stdio, no environment variables required.
- Extra arguments: forwarded verbatim from the editor setting
  (`chio.lsp.args`) to the `chio-lsp` invocation. `chio-lsp` accepts
  the same flag surface as the `chio lsp` subcommand on the unified
  `chio` binary.
- Diagnostics: every `lsp_types::Diagnostic` carries the registry code
  in its `code` field. The format is `urn:chio:error:<domain>:<code>`,
  e.g. `urn:chio:error:capability:scope-mismatch`. Editors render the
  URN unchanged; downstream tooling matches on the `code` field
  programmatically.
- Document selectors: the `chio-yaml`, `chio-manifest`, and
  `chio-guard` language IDs in the VSCode `package.json` and the
  language entries under `languages/chio/` in Zed both map to the same
  set of file suffixes (`chio.yaml`, `*.chio-manifest.yaml`,
  `*.chio-guard.yaml`).

Third-party editors (Neovim, Helix, JetBrains, Emacs lsp-mode) can
adopt `chio-lsp` against this contract without first-party packaging.
The binary ships from the `chio-lsp` Rust crate at
`crates/chio-lsp/`; the `chio` CLI also exposes `chio lsp` as an
alternative entrypoint that proxies to the same server.

## Installing locally

```bash
# Build the language server binary.
cargo build --release -p chio-lsp

# VSCode (development host).
cd editors/vscode-chio
npm install
npm run compile
# Launch the extension via "Run Extension" (F5) inside VSCode, or
# package with `npx @vscode/vsce package`.

# Zed (development extension).
# Install the extension dev bundle from editors/zed-chio/ via
# `Zed: Install Dev Extension` in the command palette.
```

## Snippets

Snippet sources live at `editors/snippets/*.snippet.yaml` and validate
against `editors/snippets/snippet.schema.json`. The xtask pipeline

```bash
cargo xtask snippets regen          # regenerate native files
cargo xtask snippets regen --check  # CI drift check (no writes)
```

renders the YAML into:

- `editors/vscode-chio/snippets/chio.code-snippets`
- `editors/zed-chio/snippets/chio.json`

Both files carry a `// generated by cargo xtask snippets regen ...`
header. CI fails the gate on drift between the YAML source and the
committed native files; reviewers must regenerate before merging.

The current pack covers four canonical patterns: capability allowlist
scaffolds, scope-bound capability fragments, guard pipelines, and
manifest skeletons. Add new entries by dropping a fresh
`*.snippet.yaml` next to the existing ones, regenerating, and
committing both the YAML and the native outputs.
